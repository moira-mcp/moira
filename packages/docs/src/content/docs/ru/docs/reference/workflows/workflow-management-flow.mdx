---
title: Workflow Management Flow
description: Долговечный evidence-aware workflow authoring с optional static progress design и independent design/artifact review.
---

Workflow Management Flow создаёт новый Moira workflow или редактирует одну полную существующую definition через source preparation, requirements, design, official tooling, independent review и явно разрешённую publication.

```bash
mcp__moira__start({
  action: "prepare",
  workflowId: "moira/workflow-management-flow",
  parentExecutionId: "none"
})
mcp__moira__start({ action: "execute", startAttemptId: "<ID попытки запуска из prepare>" })
```

## Authoring lifecycle

Flow определяет create/edit identity, online/offline source boundaries, local source hint и autonomous/interactive mode. Он материализует execution-correlated workspace с текущим authoring reference, получает полные server/repository candidates, записывает provenance и semantic differences и никогда механически не объединяет JSON.

На уровнях standard и complex requirements и full antipattern audit (по выбору при правке на уровне standard, по умолчанию при правке на уровне complex) формируют один outcome-oriented design contract, и independent pre-mutation review должен пройти до изменений полного артефакта через official workflow CLI. Результат проходит validation и официальный structural schema projection, затем independently review по полному JSON, requirements, design, authority и evidence modalities. Уровень simple строит или меняет workflow прямо по требованиям и вместо этого проходит лёгкое ревью — см. [Что запускает каждый уровень](#что-запускает-каждый-уровень).

Design contract выражает каждое решение на той ноде, у которой есть данные для него — routing `cases` и свёрнутые `expressions` на решающей ноде, `success`, когда ни один кейс не сработал, — и оставляет отдельную ноду condition или expression только для общего или самостоятельного решения; ревью считают находкой ноду маршрутизации, которая лишь маршрутизирует или считает то, что предыдущая нода уже знает (avoidable routing scaffolding). Когда этап идёт по списку, который flow хранит в переменных, дизайн привязывает блок прогресса к нему, чтобы запуск показывал done/total и текущий элемент.

Если у workflow есть содержательные пользовательские этапы, этот же lifecycle проектирует его представление процесса: короткую цепочку блоков в порядке процесса, каждый с описанием в одно предложение, где каждая нода графа, включая ноды маршрутизации, принадлежит одному блоку, каждая связь, выходящая из блока, подписана решением, которое она выражает, каждый возврат объясняет причину и выход, а хабы стоят после блоков, которые в них ведут. Ворота дизайна WMF задают это как часть контракта до мутации, ворота сборки создают это официальным CLI и завершаются только когда `derive` не показывает диагностик, а ревью проверяют, что подписи, объяснения циклов, описания и порядок соответствуют графу. Условия и маршруты исполнения остаются в основном графе workflow; запуск показывается по записанному маршруту. Единые projection и visual model используются и интерфейсом, и серверным PNG renderer, и агент может запросить короткоживущую одноразовую ссылку на этот PNG. Уведомление прикладывает картинку шагов запуска шириной телефона, построенную из той же projection, не сохраняя никакой token в состоянии workflow. WMF не добавляет progress, если он будет декоративным.

Когда один блок представляет несколько текущих ролей, WMF может спроектировать
`progressActiveLabel` на его waiting nodes. Он показывается только для точной текущей primary
node; неактивные блоки сохраняют стабильный base label. WMF требует, чтобы каждая переменная
была авторитетна на всех достигающих node маршрутах, и отклоняет stale counters, неверный scope и
progress-owned state или routing.

Artifact-owned findings исправляют workflow и повторяют stale gates. Invalid criteria или upstream process defects приводят к replan. Final report описывает точные starts, teleports, terminals, routes, cycles, reachability, coverage, data flow и каждый frozen semantic guarantee.

## Разговор о требованиях

Человек, которому нужен workflow, обычно знает свою работу, а не Мойру. Оба владельца требований — для create и для edit — читают материализованный `reference/conversation.md` и говорят на языке этой работы: для чего workflow, как человек поймёт, что запуск прошёл хорошо, а настоящие решения задают вопросом о его работе, а не о нодах и условиях. Варианты предлагаются с их ценой простыми словами — проще значит быстрее и короче; основательнее значит дольше и больше процесс, зато выше качество; процесс всегда можно доработать позже — и согласуется один из трёх уровней:

- **simple** — шаги по порядку, возможно один выбор или одно одобрение;
- **standard** — настоящие развилки, цикл «проверить и переделать», одобрения, долговечные файлы или действия, требующие полномочий человека;
- **complex** — несколько взаимодействующих циклов, подпроцессы, переходы между частями, блокировки, многоэтапное представление процесса, публикация или другие действия с высокими полномочиями, либо любой workflow, который человек хочет провести полным путём.

Когда агент о чём-то спрашивает человека или что-то предлагает, он объясняет варианты на языке человека — что значит каждый и что из него следует — и приводит доводы в пользу своей рекомендации. То же правило WMF закладывает в создаваемые workflow: паттерн простого уровня «Questions that explain and argue» требует этого везде, где агент workflow спрашивает человека, а парный антипаттерн «A bare question or an unargued proposal» заставляет ревью и аудит отмечать директиву, которая спрашивает без этого; на простом уровне лёгкое ревью задаёт это своим третьим вопросом. Собственные вопросы WMF об одобрении и загрузке и стартовая форма «гейт одобрения» следуют тому же правилу.

Интерактивный запуск подтверждает уровень у человека; автономный решает сам и записывает почему. Если запрос уже говорит, насколько основательно работать, уровень берётся из него без вопроса. Файл требований фиксирует уровень, его причину и выбранную стартовую форму, если она есть.

В рабочем пространстве также лежат три стартовые формы в `reference/templates/`, каждая — валидный workflow, от которого можно строить официальным CLI: чеклист (`checklist.json`), «сделать — проверить — переделать» (`do-check-redo.json`, это цикл проверки и переделки, поэтому уровень standard) и гейт одобрения (`approval-gate.json`). Справочники паттернов и антипаттернов сгруппированы по уровням: каждая запись стоит на самом низком уровне, где применима, поэтому раздел simple содержит только то, в чём может ошибиться короткий флоу из шагов, а механика ревью, починки, доказательств и валидаторов лежит в разделах standard и complex.

## Что запускает каждый уровень

Уровень, согласованный в требованиях, решает, какие обязанности выполняются:

- **simple** — при создании без проектирования структуры, ревью дизайна и одобрения структуры; при правке без аудита антипаттернов, плана правки, его ревью и одобрения. Workflow строится или меняется прямо по файлу требований (при создании — и по названной в нём стартовой форме), а затем проходит лёгкое ревью: неустранимый минимум (ниже) и четыре вопроса — делает ли workflow то, о чём просил человек, называет ли каждое условие завершения наблюдаемый результат, а не намерение, объясняет ли каждый шаг, который спрашивает человека, варианты и доводы рекомендации агента, и следует ли сообщение каждого уведомления правилам содержания уведомлений ([ниже](#что-могут-говорить-workflow-которые-он-создаёт)). Найденное исправляется и проверяется снова. Если починка не может воспроизвести замечание, она так и отвечает и называет, что проверила; тогда лёгкое ревью снимает замечание или переформулирует его с точными шагами воспроизведения, а замечание, не воспроизведённое второй раз, больше не отправляется в починку и передаётся человеку как открытый вопрос. Если человек отклоняет результат на финальном ревью или процесс запуска пересматривается, требования исправляются и workflow снова собирается или меняется — по-прежнему без проектирования и плана правки.
- **standard** и **complex** — полный путь: при создании проектирование структуры, независимое ревью дизайна и одобрение структуры в интерактивном запуске; при правке план правки, его независимое ревью и одобрение плана в интерактивном запуске; затем сборка и полное ревью качества. Правка на уровне standard спрашивает, проводить ли полный аудит антипаттернов; правка на уровне complex проводит его без вопроса. Ещё уровни различаются тем, какие разделы справочников применяются.

Каждая обязанность, читающая справочники паттернов и антипаттернов, применяет разделы текущего уровня и всех уровней ниже; разделы более высоких уровней не применяются.

Неустранимый минимум действует на каждом уровне: официальный CLI `validate` не сообщает ни ошибок, ни недостижимых нод — предупреждение о недостижимой ноде блокирует, — и каждый маршрут от `start` заканчивается в `end`. У workflow ровно один тег `complexity:<уровень>` в `metadata.tags`; сборка и каждая починка workflow сохраняют его вместе с остальными тегами (`set-tags` заменяет весь список), а оба ревью это проверяют. Веб-приложение показывает этот тег значком уровня — «Простой», «Стандартный» или «Сложный» — на карточке флоу и в шапке страницы флоу, отдельно от тематических тегов; у флоу без такого тега значка нет.

Ревью могут только повышать уровень. Когда лёгкое ревью, его починка или полное ревью качества обнаруживают, что workflow нужно больше, чем покрывает его уровень, они повышают уровень и называют причину. Запуск продолжается от текущих требований и уже собранного workflow, требования заново не собираются: новый workflow идёт в проектирование структуры и его независимое ревью; правка, поднятая до `standard`, получает вопрос об аудите, а поднятая до `complex` — полный аудит антипаттернов по workflow в его текущем виде, затем план правки и его независимое ревью. В интерактивном запуске агент простыми словами объясняет человеку, почему процесс вырос и чего это стоит, — при одобрении структуры (создание) или плана правки (правка) и ещё раз на финальном ревью; проектирование и автономный отчёт получают ту же причину. Ни одно ревью не может ответить более низким уровнем, а полное ревью качества повышает только до `complex`.

Ниже `complex` финальное ревью и автономный отчёт простыми словами называют, что уровень пропустил, — на `simple`, например, независимое ревью дизайна — и путь назад: запустить этот флоу снова в режиме правки этого workflow и попросить полный путь; тег `complexity:` сообщает этой правке, что не выполнялось. При правке на уровне `standard`, когда от полного аудита антипаттернов отказались, они также говорят, что весь workflow не проверялся аудитом. Оба называют открытые вопросы, которые оставило лёгкое ревью. Автономный отчёт также называет уровень, почему он выбран, и каждое повышение с причиной.

Правка начинается с уровня, записанного в workflow. Тег ниже `complex` значит, что обязанности, которые этот уровень пропускает, для него не выполнялись; если правка повышает уровень, они выполняются для всего workflow, а не только для изменённой части. Workflow без тега уровня имеет неизвестную историю, и правка определяет его уровень по самому workflow и запросу.

Уровень понижается только тогда, когда человек в интерактивном запуске прямо просит более простой процесс: в разговоре о требованиях, при одобрении структуры или плана правки либо на финальном ревью вместе с отклонением результата. Агент сначала записывает просьбу словами человека и получившийся уровень в файл требований; с этого момента запуск идёт только маршрутами более низкого уровня, а финальное ревью говорит, что выполнялось до понижения. Ни одно ревью не может понизить уровень, и автономный запуск никогда его не понижает.

## Publication и local synchronization

Server upload — отдельное решение: standard, copy-new или явно разрешённый admin override. Autonomous mode не придумывает upload authority ни при вопросе о загрузке, ни после неудачной загрузки: сам он повторяет попытку, оставляет workflow несохранённым или отменяет запуск, а copy-new или admin override выбирает, только если пользователь явно разрешил этот способ. Repository synchronization сохраняет identity выбранного target и не пишет посторонние paths. WMF создаёт definition, но не выполняет downstream task будущего workflow.

## Уведомления

WMF отправляет уведомления в настроенные каналы пользователя. У каждого сообщения заголовок —
название флоу и задача прогона, ссылкой на страницу прогона; картинок сообщения не несут. Каждая
строка из значений прогона берётся из поля в одно предложение, которое шаг пишет для человека, без
имён файлов и внутренних значений; поля перечислены ниже. Тексты сообщений — на английском.

| Когда | Interactive | Autonomous |
| --- | --- | --- |
| План готов | Standard и complex: «Workflow structure ready for your approval» или «Edit plan ready for your approval» (структура или план правки ждут согласования) с запланированными этапами или правками и вариантами — согласовать, и сборка идёт дальше, или отклонить с фидбеком. Simple: «Plan ready — the build goes ahead» (или «the changes are being applied») со списком | «Plan ready — the build goes ahead» (план готов, сборка идёт) или «the changes are being applied» со списком |
| Правка уровня standard спрашивает о полном аудите | «Audit the whole workflow first?» (сначала проверить весь workflow?): что даёт аудит и чего он стоит, и варианты | «Decided for you» (решено за вас): проверить весь workflow или планировать только запрошенную правку, и почему |
| Результат готов | «The workflow is ready for your review» (workflow ждёт проверки): согласовать, чтобы перейти к сохранению, или попросить изменения | — |
| Сохранение | «Save the workflow to your catalogue?» (сохранить в каталог?): что даёт каждый способ сохранения и отказ от сохранения | «Decided for you»: сохранить или не сохранять, и почему |
| Сохранение не удалось | «Saving the workflow failed» (сохранить не удалось): почему, и варианты — повторить, оставить несохранённым или отменить; для чужого workflow — отдельная копия или замена администратором | «Decided for you»: повторить (или способ, который разрешил пользователь) либо оставить несохранённым, и почему |
| Прогон завершён | «Workflow created» или «Workflow updated» (создан или обновлён): название и версия, сохранён ли в каталог, и запланированные этапы или правки, отмеченные выполненными | то же |
| Прогон отменён | «Cancelled» (отменено): название и версия собраны, но не сохранены, и почему | то же |

Список плана — список блока сборки: `planned_changes`, этапы нового workflow или запланированные
правки. На уровне simple его пишет владелец требований, на standard и complex — проектирование или
план правки. Каждая ревизия переписывает его — после отклонённого результата, при пересмотре
процесса и при понижении уровня на согласовании, — поэтому изменившийся план объявляется снова.
Когда план объявляется, список читается как ещё не выполненный, а после сборки — как выполненный.
Правка уровня complex проверяется аудитом без вопроса. Строки для читателя берутся из полей в одно
предложение, которые шаги пишут для человека:
- `execution_note` — задача, с первого шага;
- `decision_summary` — из решений об аудите, о загрузке и о неудачной загрузке;
- `workflow_name` и `workflow_version` — из решения о загрузке;
- `failure_summary` — при неудачной загрузке.

Исправленный план объявляется снова. Поскольку флоу отправляет уведомления, его запуск для
пользователя без настроенного канала отклоняется с инструкцией; агент, который хочет работать без
уведомлений, заново готовит запуск с `skipNotificationCheck: true`.

### Что могут говорить workflow, которые он создаёт

WMF учит тем же правилам для каждого уведомления в workflow, который он создаёт или правит.
Правила живут в справочнике движка, `reference/engine.md`:

- Заголовок добавляет движок. Он задаётся через `execution_note` на первом шаге агента, и
  сообщение его не повторяет.
- Список плана берётся из списка, привязанного к рабочему блоку, через `planList`: `full` при
  готовности плана и на каждом завершении, `progress` в остальных местах. Сообщение никогда не
  пишет список вручную.
- Никакое внутреннее значение не доходит до читателя: ни путь или имя файла, ни синтаксис
  шаблонов, ни id ноды, ни имя переменной, ни сырое значение перечисления, ни счётчик без
  названия. Строка из значений прогона берётся из поля в одно предложение, которое шаг пишет
  для человека, а значение перечисления передаётся словами.
- Место уведомления следует режиму работы. Интерактивный запуск узнаёт о вопросе до него, с
  объяснёнными вариантами и обоснованной рекомендацией. Автономному запуску никогда не говорят,
  что решение ждёт: он узнаёт, что работа идёт, и получает одно сообщение после каждого решения,
  принятого агентом, — что решено и почему, отправленное с собственного маршрута решающей ноды.
- Последнее сообщение прогона соединено прямо с `end`, поэтому в его списке ни один пункт не
  отмечен как идущий.

На уровне simple лёгкое ревью задаёт этот вопрос, а на standard и complex полное ревью качества
проверяет, что сообщение каждого уведомления следует этим правилам.
