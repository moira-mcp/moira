title: Software Development Flow
description: "Полная development-only реализация репозитория с plan-owned visual evidence, отчётами, review и локальным VCS в пределах полномочий."
---

Software Development Flow реализует одно полное программное изменение как независимо принимаемые вертикальные units. Он владеет всем результатом репозитория — production code, тестами, coverage, документацией, schemas/types, generated/config outputs, compatibility и integration consequences — вместо разделения одного lifecycle между несколькими task workflows.

```bash
mcp__moira__start({
  action: "prepare",
  workflowId: "moira/software-development-flow",
  parentExecutionId: "none"
})
mcp__moira__start({ action: "execute", startAttemptId: "<ID попытки запуска из prepare>" })
```

## Lifecycle

Flow фиксирует source-grounded требования и полномочия, определяет одну простую visual preference (`disabled`, `screenshots` или `html_report`), создаёт и независимо проверяет architecture-aware план, после чего именно текущий план становится единственным источником visual и user-approval policy каждого unit. Flow готовит каждый unit по реальному репозиторию до мутации, реализует полное вертикальное поведение и запускает fresh producer completion до deterministic validation и independent semantic review. Документация и тесты являются частью production, а не поздней уборкой.

Каждый execution также показывает постоянно видимое представление процесса из пятнадцати блоков:
Intake, Project health, Plan and plan review, Plan approval and activation, Implement a unit, Unit
validation gates, Broad validation and documentation, Independent completeness review, Unit review
with the user, Checkpoint and advance, Feature-wide validation, Final review and report, Replan,
Finalize и Stopped. Каждая нода принадлежит одному блоку, каждая связь, выходящая из блока,
подписана, а каждый возврат объясняет причину и условие выхода, поэтому переходы, циклы и
блоки-хабы выводятся из исполняемого графа. Активный блок следует за текущей primary workflow
node, поэтому repair, replan и обычный multi-unit loop из checkpoint снова открывают
соответствующий ранний блок без отдельных status variables. Уведомления не несут картинок; план в них
передаётся текстовым списком (см. [Уведомления](#уведомления)). Progress не меняет routing SDF или его
границы полномочий.

Стабильные inactive labels остаются короткими. Пока текущей является точная implementation,
validation, independent review, repair или checkpoint node, её active-only label добавляет
авторитетные unit, total и iteration для этой роли. Plan/replan nodes не используют stale unit
counters.

`screenshots` один раз снимает и действительно просматривает необходимые состояния. `html_report` переиспользует эти же принятые изображения в self-contained отчёте, загружает его через Moira Artifact API и отправляет публичный URL через настроенные каналы связи текущего пользователя; второй screenshot pass не выполняется. Сбой Artifact upload блокирует unit. Отсутствие настроенных каналов или ошибка отправки в достигнутой notification node не блокируют работу. Interactive approval плана, выбранных units и финального результата получает attention notification и ждёт решения в обычной директиве. В autonomous mode human-approval directives отсутствуют. Исключение — досрочное завершение всего запуска, и это не approval: когда блокер не снимается или unit не может быть закрыт, flow сообщает, что именно останется незавершённым, и завершает запуск только по явному подтверждению пользователя, которое autonomous mode никогда не выводит сам.

Findings классифицируются как product, test/validation, evidence, documentation/projection, invalid criterion или upstream plan/process defects. Product repair возвращается через producer completion. Verification-only и gate-local repair повторяют только устаревшие evidence. Mixed или invalid causes приводят к quality-preserving replan, а не к расширению реализации по сломанному контракту.

Каждый producer, validator, reviewer, repair role, checkpoint и report role текущего unit получает полный утверждённый unit из `plans/{{plan_revision}}/plan.md`. Эта активная ревизия остаётся источником истины после любого replan; запомненная формулировка и `previous_plan_revision` не являются входами исполнения. Только пять revision writers намеренно читают обе ревизии: они сохраняют исторический источник и записывают уже увеличенную текущую ревизию. Финальное cross-revision review может использовать исторические evidence с явным указанием ревизии происхождения, но не заменяет ими контракт активного плана.

Если исходный запрос уже разрешает последующий caller-owned push, pull request, publication, release или deployment, SDF во время intake сохраняет это намерение через `session` reminder API текущего execution. Запись требует текущую ревизию шага workflow, но не увеличивает её и не делает предъявленную попытку шага недействительной. При обычном завершении standalone и child запусков reminder возвращается в `Next requested actions`. Он не становится unit плана разработки, не меняет `vcs_commits_authorized`, не выполняет действие и не даёт новых полномочий.

Runtime, browser, visual, integration, performance и full-suite checks остаются условными для конкретной фичи и репозитория. Permanent documentation закрывается вместе со своим vertical unit; финальная reconciliation продолжает проверять cross-unit truth и независимо ревьюит только изменённую либо ранее не покрытую документацию. Финальный suffix включает feature-wide validation, semantic review, requirements coverage, factual report и локальную VCS reconciliation в пределах полномочий. Запуск завершается одним из трёх способов, и каждый отправляет best-effort уведомление через
настроенные каналы пользователя: он завершается полностью; он завершается досрочно по явному
подтверждению пользователя; либо разработка доведена до конца, а локальная финализация осталась
заблокированной — и это сообщается именно так, а не как полностью завершённый запуск.

## Уведомления

Первый шаг сохраняет [название задачи](/ru/docs/concepts/workflows/#название-задачи-запуска) с
актуальными ревизиями Progress/session до завершения. Следующая нода доставляет
`standards/planning.md`; остальные ответственные читают её контракт именования. Необязательная
`execution_note` — произвольный непустой текст до 120 символов. Ответственные за разрешённый
пересмотр требований, плана или обратной связи переименовывают запуск только при изменении самой
задачи; технические исправления сохраняют название, происхождение завершённой работы и границы delivery.

SDF отправляет уведомления в настроенные каналы пользователя. У каждого сообщения заголовок —
имя флоу и независимо сохранённое название задачи, ссылкой на страницу прогона;
картинок сообщения не несут. Каждая строка из значений прогона берётся из поля в одно предложение,
которое шаг пишет для человека: цель (`goal_summary`, переписывается при пересмотре требований), названия юнитов (`plan_units`), результат юнита (`unit_result_summary`),
блокер (`blocker_summary`), итог и ограничения. Ссылки на отчёты стоят обычными URL. Тексты сообщений
— на английском.

| Когда | Interactive | Autonomous |
| --- | --- | --- |
| Проверенный план готов | «Plan ready for your approval» (план ждёт согласования): цель, весь список юнитов, согласовать — и работа идёт по этому плану, или отклонить с фидбеком | «Plan approved — the work goes ahead on this plan» (план согласован, работа идёт по нему): цель, весь список юнитов |
| Юнит с отчётом без одобрения | «Unit N “title” is done» (юнит готов): его результат и ссылка на отчёт | то же, в том числе когда юнит просил одобрения |
| Юнит, которому нужно одобрение | «Unit N “title” is ready for your review» (юнит ждёт проверки): результат, принять или отклонить с фидбеком — со ссылкой на отчёт в том же сообщении, если отчёт есть | — (автономный запуск не останавливается на одобрении юнита) |
| Блокер на проверке здоровья, runtime-, широких или финальных проверках | «Blocked» (заблокировано): блокер и варианты — устранить его и дать агенту повторить или завершить весь запуск | то же |
| Финализация заблокирована | «Finishing is blocked» (завершение заблокировано): блокер и варианты — повторить, закончить без финального локального коммита или завершить весь запуск | то же |
| Юниту нужна смена плана | «Unit N “title” needs a plan change» (юниту нужен новый план): почему, согласовать закрытие юнита и пересмотр плана или завершить запуск | тот же юнит и причина, и что агент закроет юнит и пересмотрит план, если причина подтверждается, а иначе спросит человека, завершать ли запуск; пересмотренный план объявляется |
| Результат готов | «The result is ready for your approval» (результат ждёт согласования): итог, ограничения, ссылка на финальный отчёт, варианты и состояние каждого юнита | — |
| Запуск завершён | «Finished» (готово): итог, ограничения и дальнейшие шаги, были ли локальные коммиты, ссылка на финальный отчёт, список юнитов | то же |
| Запуск завершён без финального коммита | «Finished without the final local commit» (готово без финального коммита): блокер и что осталось, список юнитов | то же |
| Человек завершил запуск | «Stopped» (остановлено): почему, что сделанное сохраняется, а после этой точки ничего не сделано, список юнитов, если план уже есть | то же |

Сообщения с вопросом отправляются только перед шагами, которые ждут человека. Шлюзы блокеров ждут
человека и в автономном запуске, поэтому их сообщения называют варианты в обоих режимах. Остальные
автономные сообщения, включая сообщение о закрытии юнита, сообщают, что происходит, а не
спрашивают: при закрытии оно говорит, что агент делает с изменением плана.

Финальный отчёт оформляется как самодостаточная HTML-страница и загружается через Artifact API, как
отчёт юнита; обе ссылки могут быть `http` или `https` — так, как инстанс отдаёт артефакты. Последние
сообщения соединены прямо с концом запуска, поэтому в их списках ни один юнит не отмечен как идущий.
Поскольку флоу отправляет уведомления, его запуск для пользователя без настроенного канала
отклоняется с инструкцией; агент, который хочет работать без уведомлений, заново готовит запуск с
`skipNotificationCheck: true`. Ошибка уведомления не останавливает запуск.

### Ждёт вас

Шаги, где SDF ждёт вашего решения, помечены как ждущие вас: подтверждение требований, согласование
плана, приёмка единицы, закрытие единицы, финальная приёмка и шаги-блокеры (проверка здоровья,
проверка в работе, широкая и финальная проверки, финализация). Пока запуск стоит на одном из них,
страница запуска и его прогресс говорят **ждёт вас** и что от вас нужно, а сообщение с вопросом
заканчивается строкой `🙋 waiting for you`. Шаги-блокеры ждут вас и в автономном запуске — изменить
внешнее состояние или завершить запуск можете только вы, — поэтому помечены в обоих режимах; закрытие
единицы автономный запуск решает сам, и там ждущим вас не показан. Где флоу шлёт своё сообщение перед
шагом, оно и есть первое уведомление; перед подтверждением требований сообщения нет, поэтому Moira
уведомляет вас сама. Если ответа нет сутки, Moira один раз напоминает со ссылкой на запуск.

## Прогресс выполнения

Карта прогресса запуска выводится из исполняемого графа: каждая нода принадлежит одному этапу, каждая связь, выходящая из этапа, подписана, а каждый возврат объясняет причину и условие выхода. Этап реализации привязан к самому плану: `plan_units` — юниты с их `title`, `current_step_index` — юнит в работе, отсчитываемый от `1`, `completed_units` — закрытые юниты, `total_steps` — число юнитов. Поэтому данные прогресса запуска (`session progress` и API прогресса выполнения) и его уведомления показывают каждый юнит, какие выполнены и какой в работе, и сколько длился каждый проход через этап. Каждый автор плана возвращает `plan_units` — короткое название каждого юнита в порядке плана; ревью плана выводит из него `total_steps`, а активация возвращает только точку продолжения.

## Когда использовать

Используйте Software Development Flow для реализации в репозитории любого размера: его план и условные проверки масштабируются под фактическое изменение, сохраняя единый полный software lifecycle. Границы security/privacy, постоянные данные и migrations, breaking public contracts, несколько vertical units, неразрешённая архитектура и сложный rollout/recovery требуют более сильных units и evidence внутри этого же flow. Quick Task и Robust Task не заменяют software lifecycle.

Development-plan SDF может включать явно разрешённые локальные commits или checkpoints. Push, создание или merge pull request, publication, release и deployment являются работой caller или parent process и никогда не становятся development-plan units. Запуск SDF не разрешает notification, production mutation или administrative override; любой side effect остаётся ограничен originating authority.

SDF не объявляет externally writable runtime variables. Агент может просматривать registry через `session variables`, но visual settings, VCS authority, plan cursors и все остальные переменные SDF остаются read-only благодаря default-deny runtime policy.
