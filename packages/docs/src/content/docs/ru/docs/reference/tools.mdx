Moira предоставляет возможности выполнения процессов через MCP-инструменты. Каталог ниже — авторитетный справочник имён инструментов, операций, входных схем и корректных примеров входа. Сборка документации напрямую читает тот же чистый типизированный контракт, который используется при MCP-регистрации и в runtime-справке.

Описания инструментов и поддерживаемые варианты для агентов и моделей являются статической частью
этого каталога и не переопределяются через настройки базы данных. Системные runtime-инструкции
передаются отдельно при MCP-инициализации и никогда не изменяют описание инструмента.

Сервер проверяет принятую редакцию контракта инструментов аутентифицированного MCP-подключения.
При HTTP 426 `upgrade_required` переподключите или переинициализируйте это подключение для
обновления инструментов. Успешная MCP-инициализация принимает текущий каталог для этих credentials;
чтение справки или вызов старого инструмента не обходят проверку.

## Поведение инструментов

Типизированный каталог определяет допустимый ввод клиента. Ниже описаны авторизация, изменения состояния и рабочее поведение, которые нельзя выразить в JSON Schema.

### Связь с пользователем

`communication_send` отправляет обычный текст в настроенные каналы аутентифицированного
пользователя. Сервер выбирает credentials и получателей. Необязательный `channel` выбирает
настроенный канал; передавать адресата или произвольные заголовки нельзя. Сохраняются ограничения
провайдера: обычное сообщение Telegram содержит до 4096 символов.

`communication_deliver` требует нативный дескриптор хоста в `file`. Передавайте `file_id`,
`download_url` и имеющиеся метаданные имени, типа и размера без изменений; не выдумывайте ID
или URL. Если зарегистрировано несколько контроллеров, выберите возвращённую ссылку контроллера
в `owner`. Доступность определяется фактической отправкой; выбранный недоступный контроллер
не подменяется другим.

`communication_deliver_publication` использует неизменяемую `publication`, которая уже
указывает своего владельца:

```javascript
communication_deliver_publication({
  publication: "<возвращённая ссылка публикации>",
  message: "Запрошенная запись",
  kind: "document",
});
operation_get({ reference: "<возвращённая ссылка операции>" });
```

Владелец файла сохраняет байты и исходный результат доставки. Облачная Moira проверяет права
канала и передаёт источник потоком в фиксированный транспорт провайдера, не получая нативный
файл и не сохраняя временную копию. Обычному тексту владелец файлов не нужен. Доставка возвращает
ссылку исходной операции; читайте её результат без повторной отправки. Если первый ответ потерян,
найдите записи через `operation_find` у выбранного владельца и явно выберите исходную.
Отсутствие совпадений, записи или связи не доказывает, что доставки не было.
Результат workflow-уведомления с вложением предоставляет ту же `operation` для чтения;
внутренняя identity execution/visit не является отдельным публичным протоколом восстановления.

Публикация содержит полные неизменяемые байты и допускает повторное чтение до истечения срока
при действующих правах. Правки источника её не меняют. Публикация сама не отправляет сообщение,
а доставка не расходует и не продлевает публикацию. Сохраняются реальные ограничения изображений
и документов Telegram и транспорты установленных расширений.

### Назначения инструментов и ссылки среды

Обнаружение возвращает ссылки среды, контроллера, цели и установки. Копируйте их без изменений:
закодированный адрес не даёт полномочий. Действия жизненного цикла используют сохранённое
наблюдение среды. Конфликт требует нового наблюдения и явного решения, включая повторное
подтверждение удаления. Вызывающий не создаёт request ID, поколения или хеши вручную.

`command_run` принимает argv либо скрипт и необязательный текстовый stdin;
`command_run_native` вместо него требует нативный файл stdin. Ссылки операции и процесса
сохраняют исходного владельца. `operation_get` читает результат, `operation_find` находит
кандидатов, `process_output`/`process_stop` обращаются к возвращённому процессу. Каждый
явный неконтролируемый вызов — отдельное намерение; потерянный первый ответ не дедуплицируется
по тексту команды. Отсутствие записи или владельца не разрешает автоматический повтор.
Кандидата выбирают явно, даже когда он один. Общие результаты операций описывают свой вид
операции и не обязательно являются сводками среды.
Поиск возвращает безопасные метаданные и ссылки; полный исходный результат требует явного чтения.
Get и find показывают известную неопределённость как `unconfirmed`, даже если приватная запись
конечная. Подтверждённый отказ остаётся completed с `outcome.ok:false`; это не меняет сохранённую
запись и не разрешает повтор.

`operation_resume` явно продолжает только сохранённую подготовку приватного репозитория
по исходной ссылке операции его создания. Он не повторяет команды и не создаёт другой репозиторий.
Чтение результата без изменений остаётся задачей `operation_get`.

`file_read` возвращает полные UTF-8 символы, проверенную ссылку целого файла и необязательное
продолжение. Читайте по строкам или возвращённому курсору. `file_create` требует отсутствующий
путь; `file_replace` проверяет полный ожидаемый текст либо наблюдённую ссылку файла.
`file_patch` сопоставляет старый и новый текст с одним исходным состоянием без вычисляемых
вызывающим байтовых смещений или хешей. `file_upload` требует нативный дескриптор и явный путь
создания либо проверенную цель замены. `file_download` публикует полный файл по пути, выбирая
имя и тип, если они не заданы; отдельный stat не нужен. `file_preview` возвращает проверенное
нативное изображение. Явные окна ограничивают наблюдение, не задавая срок выполнения команды.

### Поиск и выполнение процессов

`list` возвращает только процессы, доступные аутентифицированному пользователю. Фильтры поиска, видимости, сортировки и пагинации применяются совместно; `total` описывает все совпадения, а не только возвращённую страницу. Каждый ответ содержит фактические `offset` и `limit`, а также `returnedCount` и `hasMore`. Если есть следующая страница, передайте `nextOffset` как `offset` следующего запроса; на последней странице возвращается `nextOffset: null`.

Все инструменты публикуют входные схемы с объектом в корне. У каждого назначения workspace
своя строгая схема; неизвестные поля и смешение назначений отклоняются до диспетчеризации.
У workflow `start` сохраняется `action` для фаз prepare/execute со строгой проверкой выбранной фазы.

`start({ action: "prepare" })` разрешает и проверяет доступный процесс, связывает версию workflow и параметры запроса и возвращает Start attempt ID со сроком 15 минут, не создавая execution. `parentExecutionId` связывает дочернее выполнение с существующим родителем; для самостоятельного выполнения используется `"none"`. `skipNotificationCheck` сохраняет политику пропуска только опционального preflight обычных уведомлений во время execute. `skipTelegramCheck` остаётся устаревшим alias с тем же поведением, а противоречащие значения отклоняются.

`start({ action: "execute", startAttemptId })` повторно проверяет изменяемые условия workflow, родителя, учётной записи, lock-delivery и связи до расходования именно этой подготовки. Workflow с `user-notification` без настроенного канала возвращает общую инструкцию по Settings, а legacy workflow с `telegram-notification` — инструкцию по настройке Telegram. Для workflow с lock node всегда нужны корректные Telegram bot token и chat ID текущего пользователя; ни один skip-флаг не обходит доверенную доставку PIN. Неуспешная изменяемая проверка сохраняет повторяемый ответ `START_PRECONDITION_CHANGED` и не создаёт execution. Успех возвращает Process ID, идентификатор попытки первого шага и первую директиву. Повторный execute возвращает точно сохранённый ответ и не может создать ещё одно execution; отдельная подготовка означает намеренный отдельный запуск.

`step` требует Process ID и идентификатор попытки шага из текущего предъявления, даже если нода принимает пустой ввод. Попытка идентифицирует предъявленный шаг и не является входными данными workflow. Повтор того же вызова с теми же входными данными возвращает долговечно сохранённый результат, не применяя переход второй раз. Одинаковые параллельные вызовы объединяются за одним владельцем: дубликат либо получает сохранённый им ответ за ограниченное время ожидания, либо получает `ATTEMPT_PROCESSING`; обработчик не выполняется последовательно для каждого дубликата. Другой ввод для завершённой попытки, попытка от другого выполнения и старая попытка после перехода процесса отклоняются.

`ATTEMPT_PROCESSING` означает, что изменение ещё принадлежит другому вызывающему: повторите ту же попытку с теми же данными. `ATTEMPT_STALE` отклоняется до работы обработчика: автоматически прочитайте `session({ action: "current_step", executionId })` и один раз повторите исходную отправку с возвращённым идентификатором попытки шага. `ATTEMPT_CONFLICT` отклоняется, потому что эта попытка уже связана с другими входными данными: автоматически прочитайте `current_step`, отбросьте конфликтующую попытку и продолжите по возвращённой директиве и схеме, не повторяя старый ввод. Если ошибка шага `ATTEMPT_INVALID_OR_EXPIRED` явно предписывает прочитать `current_step`, примените то же восстановление и отбросьте недоступную попытку. Для недоступной попытки запуска такое восстановление неприменимо. `ATTEMPT_OUTCOME_UNKNOWN` означает, что внешний эффект уже мог произойти: изучите возвращённый Process ID и не повторяйте изменение автоматически. Владелец может завершить заблокированное execution на его текущей ревизии через `session({ action: "cancel-execution", executionId, expectedRevision })`. Каждое последующее приостановленное предъявление получает новый идентификатор попытки. Процесс может предоставлять именованные точки телепортации; телепортация и обычный ввод ноды взаимоисключающие. Зарезервированное поле `execution_note` во входе обновляет заметку, видимую в списках выполнений. Ошибки инструмента остаются ошибками и не отображаются как успешные шаги.

`session` работает только с выполнениями текущего пользователя. Он позволяет получить сведения о пользователе, перечислить или исследовать выполнения, повторно показать текущий шаг без продвижения, выяснить, почему приостановленное выполнение не может продолжиться, изменить заметку или родителя, управлять напоминаниями вызывающей стороны, читать и изменять объявленные runtime-переменные согласно политике процесса, читать прогресс или запросить одноразовое скачивание изображения прогресса, поднять вопрос агента к пользователю, а также доставить файлы приостановленной ноды материализации прямо в ответ, когда хост не может выполнить предъявленную команду. `await-user` нужен в момент, когда агент не может продолжить без пользователя: он записывает `question` (до 500 символов) и необязательные `options` (до четырёх вариантов) на идущее выполнение, привязывая их к шагу, на котором стоит запуск, и запуск показывается ждущим пользователя с этим вопросом, а пользователь получает уведомление в свои каналы с вопросом, вариантами и ссылкой на запуск (новый вопрос раньше чем через десять минут после прошлого уведомления ждёт до этого срока); пользователь отвечает агенту в его чате, а не в Мойре. Новый вызов заменяет вопрос, `resolve: true` снимает его. Его снимают и следующий шаг агента (принятый или отклонённый), переменная, заданная агентом через `set-variable`, восстановление, отмена и завершение, а также уход запуска с этого шага; правка человека на странице запуска — нет. Вызов не меняет ревизию шага, поэтому предъявленная попытка шага остаётся действительной, а `execution_context` возвращает открытый вопрос как `awaitingUser`. После прерывания `current_step` возвращает авторитетное текущее предъявление и его идентификатор попытки шага. Если у приостановленного выполнения нет сохранённой попытки шага, `current_step` создаёт привязанное предъявление без исполнения или продвижения ноды. Он также исправляет предъявленную попытку, у которой устарела только привязка к ревизии выполнения. Для живой попытки, привязанной к другой ноде или к поверхности продолжения, которой в текущем определении больше нет, возвращается `CURRENT_PRESENTATION_STALE`; её старый идентификатор не рекомендуется и не может быть повторён, а сама ошибка указывает на `diagnose`. `diagnose` сообщает, может ли приостановленное выполнение продолжиться на текущем определении workflow, и называет каждую причину, по которой не может: ноду, на которой оно стоит, и сохранилась ли она; какие факты его поверхности продолжения изменились; какие ссылки предъявленный шаг не может разрешить из контекста; записанную ошибку выполнения; попытку, принадлежащую другой ноде, без привязки продолжения или не в состоянии предъявления. Каждая причина сообщает, блокирует ли она продолжение: блокирующая означает, что без восстановления выполнение не дойдёт до следующего шага, а неблокирующая объясняет наблюдаемое, пока выполнение остаётся пригодным, — отсутствующее или устаревшее по ревизии предъявление, попытка, которую исполняет другой вызывающий, неразрешённая ссылка, записанная ошибка. Поле `continuable` истинно, когда не блокирует ни одна причина. Действие ничего не меняет, а здоровое выполнение сообщает о себе как о пригодном к продолжению и не называет ни одной причины. `recover` возвращает такое выполнение к шагу, с которого оно может продолжиться: передайте `nodeId` ноды, на которой выполнение может ожидать, — agent-directive, teleport, materialize, lock или subgraph — и `variableValues` с тем, что этому шагу нужно, — выполнение переносится туда, значения записываются в контекст, нода предъявляется заново, и следующим вызовом становится обычный `step()`. Действие отклоняется для выполнения, которое уже завершено: завершённое или отменённое выполнение таким и остаётся, потому что восстановление чинит то выполнение, которое пытается продолжиться и не может, а `diagnose` по-прежнему объясняет, почему оно не может продолжиться. Для ещё идущих выполнений действие отклоняется, если `diagnose` не называет ни одной блокирующей причины: здоровое выполнение отклоняется намеренно. Любой отказ оставляет выполнение нетронутым и называет следующие вызовы. В аудит записываются оба исхода: и восстановление, и отказ. Поверхность продолжения — это то, от чего ещё зависит приостановленный шаг: всё, что объявляет эта нода, кроме того, как она отображается (в том числе пометки `humanGate`, которая меняет лишь то, кого запуск показывает ждущим), плюс записи реестра для объявленных ею на вход глобальных переменных. Поэтому обновлённый workflow оставляет приостановленное выполнение пригодным, пока изменение её не затрагивает: новая версия, новые теги, переписанное описание, правка другой ноды или чисто косметическое изменение самой приостановленной ноды пригодность сохраняют.

Если выражение ноды agent-directive читает сохранённую переменную верхнего уровня, которой нет в execution, `diagnose` сообщает блокирующую причину `missing_expression_variables`, когда Moira может установить, что значение нельзя передать полем ответа, разрешённым одновременно входной схемой и объявлением выходных полей верхнего уровня, а у ноды нет заданного пути обработки ошибки. Открытая входная схема сама по себе не делает необъявленное поле ответа пригодным. Объявленное выходное поле тоже не может передать значение, если входная схема запрещает его, например через `maxProperties: 0`, схему свойства `false` или запрет внутри `allOf`. Если Moira не может доказать запрет по ограничениям схемы, поле остаётся доступным для ответа, а некорректный ответ нужно исправлять обычным способом. Неуспешный `step`, вызванный именно отсутствующим значением, и `current_step` направляют агента к `diagnose` и `recover`. Передайте названные значения через `recover` с текущим `nodeId`; объявленные переменные должны соответствовать своим схемам в реестре. Отсутствующие или некорректные значения приводят к отказу без изменения выполнения. Успешное восстановление заново предъявляет ту же ноду со свежим идентификатором попытки; затем отправьте обычный ответ через `step`. Неверный по схеме ответ и ошибка выражения, вызванная данными ответа, по-прежнему требуют исправления ответа, даже если диагностика также называет более позднее отсутствующее сохранённое значение: сначала исправьте текущую ошибку ответа. Заданный путь обработки ошибки выполняется как обычно. Одна лишь записанная в прошлом ошибка не открывает восстановление здорового выполнения.

При обычном продвижении исходный вызов `step` увеличивает ревизию, когда сохраняет состояние workflow; `stop-execution` также увеличивает её один раз при остановке. Изменения родителя, напоминаний, заметки и runtime-переменных не увеличивают её и не делают текущую попытку шага недействительной. Для записи родителя, напоминаний и runtime-переменных нужны `expectedRevision` и соответствующая непрозрачная ревизия из `execution_context`, `reminders`, `variables` или предыдущего изменения (`expectedParentRevision`, `expectedRemindersRevision` или `expectedContextRevision`). Эти ревизии отдельных целей не дают старому снимку метаданных перезаписать более новый в рамках одной генерации шага. Изменение родителя принимает `"none"` для отсоединения, требует выполняющиеся execution одного владельца и отклоняет циклы. Напоминания не меняют план workflow и не дают полномочий; активные напоминания возвращаются при завершении execution. Запись runtime-переменных по умолчанию запрещена, обязана соответствовать схеме переменной и не продвигает граф. Запись по устаревшей ревизии отклоняется до любых изменений; её `AGENT INSTRUCTIONS` велят перечитать это состояние и повторить вызов с текущими ревизиями, не привлекая пользователя.

Для приостановленной ноды materialize `current_step` возвращает команду архива на пять минут,
а не тела файлов. Выполните её без изменений и после успешной распаковки завершите шаг `null` или `{}`.
Первый запрос архива materialize разрешает авторизованный текст и закрепляет полную identity
сопряжённого контроллера вместе с исходным ID публикации. Повтор того же пятиминутного разрешения
читает публикацию без нового обращения к источникам, рендера или отправки. Правка workflow не
меняет её байты. Отсутствующий или неопределённый исход возвращает HTTP 409 с
`COMMUNICATION_OUTCOME_UNCONFIRMED` и `request_id`; чтение не повторяет операцию.
Завершённая ошибка владельца возвращает HTTP 422, недоступный контроллер — HTTP 503 с
`COMMUNICATION_OWNER_UNAVAILABLE`. Новый показ текущего шага нужен только для отдельной явной
попытки. Проверки пользователя, ноды и контекста сохраняются. Текстовый fallback `materialize`
не требует владельца файлов и имеет отдельный бюджет ответа 256 KiB.

`update-task-title` задаёт или меняет название активной задачи владельца независимо от заметок.
Прочитайте `execution_context` и передайте его `revision` и `metadataRevisions.taskIdentity` как
`expectedRevision` и `expectedTaskIdentityRevision`. Нормализованное непустое название ограничено
500 кодовыми единицами строки JavaScript; управляющие и форматирующие символы Unicode запрещены
до удаления пробелов. Обе ревизии проверяются и при том же нормализованном названии; его успешный
повтор не меняет активность или события. Именование сохраняет попытку шага и другие метаданные.
Завершённые и остановленные запуски отклоняют его. Вызов и порядок подстановки описаны в
[контракте именования](/ru/docs/concepts/workflows/#название-задачи-запуска). Без авторского процесса
чтение прогресса возвращает `source: "metadata"`, без выдуманных блоков и без ошибки;
авторская проекция сохраняет `source: "trace"`.

Восстановление на materialize оставляет ноду на паузе для доставки. Разрешение получает текущие
значения реестра по умолчанию; изменение контекста само по себе не обновляет файлы вызывающей
стороны. Выполните доставку до завершения ноды.

Разрешения на PNG требуют авторского прогресса и привязаны к владельцу, версии workflow, ревизиям
шага, контекста и независимого названия, а также параметрам рендера. Переименование, в том числе
возврат к прежнему тексту при том же времени часов, делает прежнее разрешение недействительным.
Устаревший запрос не расходует его успешно; получите новое разрешение, также если в нём нет
привязки к названию. Ошибка рендера или HTTP-доставки освобождает резервирование; успешное
завершение ответа расходует разрешение один раз.

PNG рисует и публикует сопряжённый контроллер с действующей регистрацией. Выберите его через `device_id` в
`session({ action: "progress-image-token", executionId, device_id })`, если зарегистрировано несколько
контроллеров, даже когда подключён только один; без этого поля нужен ровно один зарегистрированный
контроллер. Фактическая отправка проверяет доступность выбранного контроллера без подмены другим.
`COMMUNICATION_OWNER_UNAVAILABLE` возвращается
как кодированная ошибка MCP и HTTP 503 при выдаче или публичном чтении. Восстановите сопряжённое
соединение вместо пересоздания VM. Обычный прогресс и текстовые уведомления не требуют владельца;
недоступная необязательная картинка пропускается с независимой попыткой доставки текста.

Одноразовый URL прогресса и неизменяемая публикация владельца имеют разные сроки.
Успешное завершение HTTP расходует разрешение прогресса; ошибка рендера или потока освобождает
резервирование, а завершение ответа с ошибкой не расходует его. Публикация допускает повторное
чтение до собственного истечения при действующих правах.

### Остановка запуска

Если пользователь отменяет идущий workflow или хочет продолжить вне него, вызовите
`session({ action: "stop-execution", executionId, expectedRevision, reason })`. Передайте текущую
`revision` из ответа `execution_context` как `expectedRevision`. Запуск должен принадлежать
вызывающему пользователю, а `reason` должен содержать 1–500 символов после удаления пробелов по
краям. Операция окончательно завершает запуск, сохраняет `stopReason`, снимает ожидания и один раз
увеличивает ревизию; успешное выполнение задачи она не подтверждает.
Ожидающие уведомления снимаются, но уже начатая доставка уведомления может завершиться.

Пока операция исполнения, в том числе восстановление или ответ со страницы запуска, выполняется,
остановка отклоняется: дождитесь её окончания и
перечитайте контекст. Устаревшая ревизия или уже завершённый запуск приводят к отказу без изменений.
Повтор успешной остановки с исходной ревизией и той же очищенной причиной возвращает тот же
результат без новой записи. `execution_context` и `executions` возвращают `stopReason`; сводка
показывает такие запуски как **Остановлен** и скрывает их по умолчанию, в том числе дочерние.
Найдите их через фильтр **Остановленные** или **Все**. Идущий дочерний запуск остановленного родителя
остаётся активным и показывается отдельно со ссылкой на родителя.

`cancel-execution` остаётся отдельной операцией для завершения заблокированного запуска.

### Определения процессов и сверка

`manage` разрешает идентификаторы процессов только в пределах доступа вызывающей стороны. Создание и редактирование валидируют итоговое определение до сохранения. Существующий идентификатор перезаписывается только по явному запросу; редактирование отклоняет пустые изменения, отсутствующие или повторные ноды и невалидный итоговый граф.

Операция `get` возвращает все заданные метаданные процесса, реестр переменных, runtime-политику, представление прогресса, напоминание и структурные сведения. `includeNodes: false` исключает только определения нод, а `includeValidation: false` — только результаты валидации. Используйте `list-nodes` для компактного обзора, `get-nodes` для выбранного набора, `analyze-variables` для анализа переменных всего определения и `set-visibility` для переключения собственного процесса между публичным и приватным режимами.

Поиск нод использует ограниченные RE2-совместимые выражения, если запрос содержит синтаксис регулярного выражения, и переходит к регистронезависимому буквальному поиску для некорректных или неподдерживаемых шаблонов. Клонирование отклоняет отсутствующий источник или повторный целевой идентификатор. Перемещение меняет порядок массива, не переписывая заданные соединения, и отклоняет результат, который перестал проходить валидацию.

Операции с переменными процесса работают с объявленным в определении `variableRegistry`. Создание, просмотр и отзыв общего доступа и приглашений требуют полномочий владельца. Неуспешная мутация возвращает MCP-ошибку без частичного применения изменения.

`reconciliation` разрешает конфликты между предыдущей встроенной версией процесса, текущей версией в базе и входящей версией образа. Статус доступен агентам, но полные состояния кандидатов показываются только администраторам; получение кандидата и разрешение конфликта доступны только администратору. Разрешайте конфликт семантически через Workflow Management Flow, а не механическим слиянием JSON графа.

### Блокировки

`lock` принимает только выполнения текущего пользователя. Статус возвращает активную блокировку, список — публичную историю блокировок, а разблокировка проверяет переданный PIN по активной записи. Для создания через MCP нужен выполняющийся процесс без активной блокировки и корректные Telegram-настройки текущего пользователя. Сгенерированный PIN отправляется только в настроенный chat, а несекретные метаданные возвращаются после успешной доставки. При отсутствующих или некорректных настройках и при ошибке отправки эта попытка не оставляет доступной активной блокировки; MCP-ответы и ошибки никогда не содержат PIN.

Отдельный аутентифицированный Web-маршрут создания блокировки один раз показывает PIN человеку — владельцу выполнения. Этот человеческий ответ недоступен через MCP или output workflow node.

### Настройки и заметки

`settings` читает один точный `key`, одну `category` или полный доступный набор. Не объединяйте `key` и `category` в одном запросе get. Определения включают настройки из базы данных и настройки, объявленные в манифестах установленных расширений. Зашифрованные значения всегда маскируются: для настроек из базы возвращается `[encrypted]`, а для настроек расширений — маска из точек с последними четырьмя символами. Административные значения и определения скрыты от пользователей без прав администратора. Запись требует существующее определение и применяет административные ограничения, объявленный тип, опциональную валидацию по JSON Schema, объявленные минимум и максимум встроенной числовой настройки, шифрование и регистрацию Telegram webhook при сохранении токена бота. Структурированное JSON-значение должно проходить сериализацию и чтение без пропуска или преобразования данных. Значение по умолчанию расширения должно пройти ту же проверку типа и схемы до принятия манифеста. Список возвращает доступные сейчас определения, а не сохранённые значения; удаление расширения скрывает его определения, но сохраняет пользовательские значения для последующей переустановки.

`notes` хранит изолированный по пользователям версионируемый текст. При чтении можно выбрать сохранённую версию; удаление мягкое. Сохранение соблюдает настроенные ограничения размера одной заметки, общего хранилища, числа версий, ключей и тегов. Администраторы могут менять действующие лимиты.

### Playbooks

`playbooks` хранит именованный переиспользуемый текст поведения — стандарт ревью, тон, определение
готовности — в одном месте, а не внутри процессов, которые на него опираются: текст правится один
раз, и агент читает его там, где он нужен.

Имя состоит из строчных букв, цифр и дефисов и уникально внутри аккаунта; запись под именем, которое
занято у другого пользователя, создаёт собственный playbook, а не меняет чужой. Каждое сохранение пишет ревизию, `restore` пишет новую ревизию с прежним
текстом, а `compare` показывает разницу двух ревизий построчно. Ревизии хранятся в пределах
настроенного удержания, размер playbook ограничен.

`visibility` публикует playbook или снова делает его приватным. Опубликованный playbook читает любой
аутентифицированный пользователь, назвав владельца, а менять его может только владелец: публикация
отдаёт текст, а не управление им. Чтобы прочитать чужой опубликованный playbook, владельца нужно
назвать через `owner` — по handle или по идентификатору пользователя.

### Публичные артефакты и файлы процессов

`artifacts` управляет публичными статическими HTML-результатами с пользовательскими квотами количества и объёма, ограничением размера файла и сроком хранения. Загрузку можно связать с выполнением; обновление и удаление требуют владения. Операция токена создаёт одноразовое HTTP-разрешение для внешнего клиента загрузки. Администраторы могут менять действующие квоты глобально или для пользователя.

`token` предназначен только для файлового импорта и экспорта процессов. Разрешение загрузки принимает JSON-файл процесса как multipart-поле `workflow`; разрешение скачивания требует доступный процесс. Оба имеют короткий срок действия. Для обычного просмотра и изменения процесса используйте `manage`.

Получив разрешение загрузки от `token`, отправьте выбранный файл на его `uploadUrl`:

```bash
curl -X POST "${uploadUrl}" -F "workflow=@your-workflow.json"
```

### Кодспейсы разработки

`workspace_list` находит собственные Local и GitHub-среды и отделяет недоступные идентичности
от наблюдённых сред. `workspace_targets` возвращает разрешённые репозитории, контроллеры и
установки. Недоступная идентичность допускает только наблюдение, без выдуманных состояния,
машины или поколения. Ошибки провайдеров видны отдельно от доступных соседних сред.

Используйте `workspace_create` с возвращённой целью и веткой. `workspace_lifecycle`
запускает, останавливает или продолжает подготовку Local по сохранённой ссылке среды.
`workspace_adopt` назначает наблюдённую GitHub-среду явно выбранному контроллеру;
`workspace_adopt_external` подготавливает собственную среду по известному имени провайдера.
`workspace_delete` требует `confirm_delete: true` и сохранённую ссылку.
Конфликт требует `workspace_observe` и нового решения без автоматического обновления
предусловий. `workspace_setup_help` объясняет недостающую настройку без создания среды.

У каждой Local-среды своя VM и постоянные файлы; один репозиторий может иметь несколько VM.
Сохраняются действующее разрешение владельца и точные права репозитория. Настройки владельца
определяют допуск ресурсов Local. Значения CPU/RAM/Docker по умолчанию относятся к новым VM,
а не меняют профили существующих. GitHub требует действующих прав аккаунта/App, личной оплаты
и явно выбранного сопряжённого контроллера. Выбор основан на регистрации, без подмены по доступности.
Политика простоя действует для новых GitHub Codespaces: отключение автоостановки задаёт максимум
GitHub 240 минут, а не бесконечную работу. Команда без вывода может быть прервана провайдером.

Local `resume_setup` продолжает подготовку той же доказанной VM после исправления предпосылки.
Обычный start и подтверждение custody остаются отдельными действиями. Неизвестное создание —
чтение исходной операции, а не разрешение заменить VM. Готовность Unix API не зависит от
удалённой регистрации; MCP дополнительно требует действующий авторизованный маршрут.
Наблюдённое remote-состояние различает отсутствие настройки, недоступность регистрации,
подключение, связь, недоступность связи и отказ. Временный обрыв допускает переподключение;
подтверждённый отказ отзывает удалённые полномочия. Команды не повторяются.

`repository_admit` запрашивает допуск существующего приватного репозитория через возвращённый
контроллер и GitHub ID репозитория. `repository_create` использует этот контроллер, возвращённую
установку и имя. Обязательны действующая делегация владельца и права проверенного личного аккаунта.
Агент не меняет согласие и не задаёт права. Незавершённое создание сохраняет исходную операцию
и подтверждённую GitHub-идентичность. Исправьте права/доступ установки, прочитайте результат через
`operation_get` и явно продолжите через `operation_resume`, когда это указано; не создавайте
другой репозиторий. Неизвестное создание использует сохранённый маркер, не чужое совпадающее имя.

Git/PR используют производные ограниченные credentials; исходные OAuth/refresh credentials
остаются на сервере. Обычные Git fetch/push подчиняются правам репозитория. `pull_request_create`
возвращает операцию; после неопределённости читайте её и используйте `pull_request_read`
с head/base либо номером перед намеренным созданием другого PR. Неопределённость хранения или
удаления credentials не является подтверждённым отказом. Сохраните исходную ссылку и следуйте
указаниям security-collection. Токены не попадают в файлы проекта, аргументы, окружение или ответы.

Команды, сессии и полный вывод принадлежат общему гостевому владельцу и постоянному журналу.
В облаке нет очереди офлайн-команд и отдельной копии результатов. Потеря наблюдения не отменяет
команду; остановка провайдера может её прервать. `timeout_seconds` задаётся явно, окна вывода
не ограничивают сохранённый вывод. Отмена остаётся неподтверждённой до доказанного физического
завершения. Именованные сессии явно открываются или продолжаются; их нельзя считать пережившими
перезапуск гостя. Изменения файлов используют ограниченные дескрипторы, проверенное исходное
состояние и атомарные транзакции; восстановление сохраняет неопределённость и чужие изменения.

Нативный ввод поступает потоком владельцу без base64 и облачного хранилища вложений.
Права проверяются до получения источника; окончательный допуск может отказать и после подготовки
ввода. Продолжение файлов/вывода сохраняет полные UTF-8 символы. Бинарные файлы требуют download
вместо потерь при текстовом декодировании. Download возвращает неизменяемые resource link и
ссылку публикации с размером, digest и сроком; ограничение не превращает префикс в полный файл.
Preview проверяет полный контейнер PNG/JPEG, не декодированные пиксели. Сохраняются явные пределы
наблюдения, физическое место, владение файлами, права и реальные пределы провайдера; общих квот
длительности команд, вывода и передачи файлов нет.

#### Прямой доступ через гостевой терминал

Установленный `moira-workspace` использует того же владельца через Unix API и те же назначения.
Смотрите поддерживаемые параметры в `--help`:

```bash
moira-workspace exec -- npm test
moira-workspace get "$OPERATION_REF"
moira-workspace output "$PROCESS_REF" --stream stdout
moira-workspace read README.md
moira-workspace patch README.md --old "Old text" --new "New text"
```

Копируйте возвращённые ссылки в последующие вызовы. Каждое намеренное изменение — новое намерение;
вызывающий не задаёт request ID, автоматического повтора нет. `find` находит исходные записи для
явного выбора. `native-upload`, `exec --native-stdin` и `deliver --native` читают нативный
дескриптор из stdin, не из аргументов. Файлы и PR используют проверенные ссылки и смысловые
параметры; публикация и доставка остаются разными действиями. Локальная работа не требует
облачной регистрации; облачное чтение результата требует зарегистрированного авторизованного владельца.
Установка через общий образ или Feature описана в
[self-hosting](/ru/docs/getting-started/self-hosting/#подключение-локальных-кодспейсов).

### Runtime-справка

`help` обнаруживает файловые темы в установленном корпусе MCP-справки и перечисляет рядом с ними прямую тему `tools`. Вызовите его без темы, чтобы получить актуальные имена тем и псевдонимы. Несколько запрошенных тем возвращаются вместе с разделителями. Тема `tools` и её псевдоним `tool` отображают тот же типизированный каталог непосредственно из реестра.
