Moira предоставляет возможности выполнения процессов через MCP-инструменты. Каталог ниже — авторитетный справочник имён инструментов, операций, входных схем и корректных примеров входа. Сборка документации напрямую читает тот же чистый типизированный контракт, который используется при MCP-регистрации и в runtime-справке.

Описания инструментов и поддерживаемые варианты для агентов и моделей являются статической частью
этого каталога и не переопределяются через настройки базы данных. Системные runtime-инструкции
передаются отдельно при MCP-инициализации и никогда не изменяют описание инструмента.

## Поведение инструментов

Типизированный каталог определяет допустимый ввод клиента. Ниже описаны авторизация, изменения состояния и рабочее поведение, которые нельзя выразить в JSON Schema.

### Связь с пользователем

`communication` доставляет сообщения только в активные каналы аутентифицированного пользователя.
Провайдеров и получателей выбирает сервер; вызывающая сторона не может передать пользователя,
провайдера, адресата, credentials, локальный путь, удалённый URL или произвольный HTTP-заголовок.
Операция `send` принимает непустое сообщение длиной не более 4096 символов и возвращает безопасную
сводку по всем настроенным каналам.

Для изображения или документа вызовите `attachment-token` с сообщением, видом вложения, именем
файла, MIME-типом и точным размером в байтах. Возвращённый grant действует пять минут и разрешает не
более одной попытки провайдера. Не помещайте grant в URL; отправьте байты с OAuth или постоянным MCP
Bearer credential пользователя, который создал grant:

```bash
curl --request POST "$uploadUrl" \
  --header "Authorization: Bearer $MOIRA_MCP_TOKEN" \
  --header "X-Moira-Communication-Grant: $grant" \
  --header "Content-Type: application/pdf" \
  --header "Content-Length: $(wc -c < report.pdf)" \
  --data-binary @report.pdf
```

Объявленный размер должен совпадать с `Content-Length` и фактически полученным числом байтов.
Размер одного вложения ограничен 20 МиБ; изображения принимаются в PNG или JPEG, а документы не
принимают image MIME-типы. До начала доставки провайдером ошибка MIME-типа, размера, сигнатуры
изображения или допуска по числу одновременных загрузок освобождает grant для исправленного запроса
до истечения срока. После любой попытки провайдера результат окончателен, а повтор возвращает тот же
неспецифичный ответ о недействительном grant. Один пользователь может одновременно иметь десять
активных grants и два буфера загрузки общим объёмом не более 40 МиБ; установка принимает одну тысячу
активных grants. Истёкшие и завершённые grants не занимают квоту выдачи.

### Поиск и выполнение процессов

`list` возвращает только процессы, доступные аутентифицированному пользователю. Фильтры поиска, видимости, сортировки и пагинации применяются совместно; `total` описывает все совпадения, а не только возвращённую страницу. Каждый ответ содержит фактические `offset` и `limit`, а также `returnedCount` и `hasMore`. Если есть следующая страница, передайте `nextOffset` как `offset` следующего запроса; на последней странице возвращается `nextOffset: null`.

Все инструменты публикуют входную схему с объектом в корне, чтобы MCP-клиенты видели полный
каталог. Поэтому публичная схема `start` содержит `action` непосредственно в корне и перечисляет
поля обеих фаз. Runtime-валидация по-прежнему строго проверяет выбранную фазу: для `prepare` нужны
`workflowId` и `parentExecutionId`, а для `execute` — `startAttemptId`; поля только другой фазы и
неизвестные поля отклоняются как MCP-ошибки. Инструмент `codespace` следует тому же шаблону в
большем масштабе: один плоский объект с `action` и полями всех действий, где обязателен только
`action`, а точная форма запрошенного действия проверяется при диспетчеризации (новый запрос либо
возобновление только с `codespace_id` и `operation_id`; для `exec` ровно одно из `stdin_text` или
`stdin_file`). Поле, которого нет ни у одного действия, по-прежнему отклоняется как MCP-ошибка; поле
_другого_ действия отклоняется при диспетчеризации как `CODESPACE_REQUEST_INVALID`. Значение по
умолчанию, объявленное действием, применяется там же и поэтому отсутствует в публичной схеме. Если два
действия принимают одно и то же поле с разными пределами — `max_bytes` равен 1 МиБ для `search` и
4 МиБ для `download`, — схема показывает обе формы, а какая из них требовалась от вызова, решает
названное действие.

`start({ action: "prepare" })` разрешает и проверяет доступный процесс, связывает версию workflow и параметры запроса и возвращает Start attempt ID со сроком 15 минут, не создавая execution. `parentExecutionId` связывает дочернее выполнение с существующим родителем; для самостоятельного выполнения используется `"none"`. `skipNotificationCheck` сохраняет политику пропуска только опционального preflight обычных уведомлений во время execute. `skipTelegramCheck` остаётся устаревшим alias с тем же поведением, а противоречащие значения отклоняются.

`start({ action: "execute", startAttemptId })` повторно проверяет изменяемые условия workflow, родителя, учётной записи, lock-delivery и связи до расходования именно этой подготовки. Workflow с `user-notification` без настроенного канала возвращает общую инструкцию по Settings, а legacy workflow с `telegram-notification` — инструкцию по настройке Telegram. Для workflow с lock node всегда нужны корректные Telegram bot token и chat ID текущего пользователя; ни один skip-флаг не обходит доверенную доставку PIN. Неуспешная изменяемая проверка сохраняет повторяемый ответ `START_PRECONDITION_CHANGED` и не создаёт execution. Успех возвращает Process ID, идентификатор попытки первого шага и первую директиву. Повторный execute возвращает точно сохранённый ответ и не может создать ещё одно execution; отдельная подготовка означает намеренный отдельный запуск.

`step` требует Process ID и идентификатор попытки шага из текущего предъявления, даже если нода принимает пустой ввод. Попытка идентифицирует предъявленный шаг и не является входными данными workflow. Повтор того же вызова с теми же входными данными возвращает долговечно сохранённый результат, не применяя переход второй раз. Одинаковые параллельные вызовы объединяются за одним владельцем: дубликат либо получает сохранённый им ответ за ограниченное время ожидания, либо получает `ATTEMPT_PROCESSING`; обработчик не выполняется последовательно для каждого дубликата. Другой ввод для завершённой попытки, попытка от другого выполнения и старая попытка после перехода процесса отклоняются.

`ATTEMPT_PROCESSING` означает, что изменение ещё принадлежит другому вызывающему: повторите ту же попытку с теми же данными. `ATTEMPT_STALE` отклоняется до работы обработчика: автоматически прочитайте `session({ action: "current_step", executionId })` и один раз повторите исходную отправку с возвращённым идентификатором попытки шага. `ATTEMPT_CONFLICT` отклоняется, потому что эта попытка уже связана с другими входными данными: автоматически прочитайте `current_step`, отбросьте конфликтующую попытку и продолжите по возвращённой директиве и схеме, не повторяя старый ввод. Если ошибка шага `ATTEMPT_INVALID_OR_EXPIRED` явно предписывает прочитать `current_step`, примените то же восстановление и отбросьте недоступную попытку. Для недоступной попытки запуска такое восстановление неприменимо. `ATTEMPT_OUTCOME_UNKNOWN` означает, что внешний эффект уже мог произойти: изучите возвращённый Process ID и не повторяйте изменение автоматически. Владелец может завершить заблокированное execution на его текущей ревизии через `session({ action: "cancel-execution", executionId, expectedRevision })`. Каждое последующее приостановленное предъявление получает новый идентификатор попытки. Процесс может предоставлять именованные точки телепортации; телепортация и обычный ввод ноды взаимоисключающие. Зарезервированное поле `execution_note` во входе обновляет заметку, видимую в списках выполнений. Ошибки инструмента остаются ошибками и не отображаются как успешные шаги.

`session` работает только с выполнениями текущего пользователя. Он позволяет получить сведения о пользователе, перечислить или исследовать выполнения, повторно показать текущий шаг без продвижения, выяснить, почему приостановленное выполнение не может продолжиться, изменить заметку или родителя, управлять напоминаниями вызывающей стороны, читать и изменять объявленные runtime-переменные согласно политике процесса, читать прогресс или запросить одноразовое скачивание изображения прогресса, а также доставить файлы приостановленной ноды материализации прямо в ответ, когда хост не может выполнить предъявленную команду. После прерывания `current_step` возвращает авторитетное текущее предъявление и его идентификатор попытки шага. Если у приостановленного выполнения нет сохранённой попытки шага, `current_step` создаёт привязанное предъявление без исполнения или продвижения ноды. Он также исправляет предъявленную попытку, у которой устарела только привязка к ревизии выполнения. Для живой попытки, привязанной к другой ноде или к поверхности продолжения, которой в текущем определении больше нет, возвращается `CURRENT_PRESENTATION_STALE`; её старый идентификатор не рекомендуется и не может быть повторён, а сама ошибка указывает на `diagnose`. `diagnose` сообщает, может ли приостановленное выполнение продолжиться на текущем определении workflow, и называет каждую причину, по которой не может: ноду, на которой оно стоит, и сохранилась ли она; какие факты его поверхности продолжения изменились; какие ссылки предъявленный шаг не может разрешить из контекста; записанную ошибку выполнения; попытку, принадлежащую другой ноде, без привязки продолжения или не в состоянии предъявления. Каждая причина сообщает, блокирует ли она продолжение: блокирующая означает, что без восстановления выполнение не дойдёт до следующего шага, а неблокирующая объясняет наблюдаемое, пока выполнение остаётся пригодным, — отсутствующее или устаревшее по ревизии предъявление, попытка, которую исполняет другой вызывающий, неразрешённая ссылка, записанная ошибка. Поле `continuable` истинно, когда не блокирует ни одна причина. Действие ничего не меняет, а здоровое выполнение сообщает о себе как о пригодном к продолжению и не называет ни одной причины. `recover` возвращает такое выполнение к шагу, с которого оно может продолжиться: передайте `nodeId` ноды, на которой выполнение может ожидать, — agent-directive, teleport, materialize, lock или subgraph — и `variableValues` с тем, что этому шагу нужно, — выполнение переносится туда, значения записываются в контекст, нода предъявляется заново, и следующим вызовом становится обычный `step()`. Действие отклоняется для выполнения, которое уже завершено: завершённое или отменённое выполнение таким и остаётся, потому что восстановление чинит то выполнение, которое пытается продолжиться и не может, а `diagnose` по-прежнему объясняет, почему оно не может продолжиться. Для ещё идущих выполнений действие отклоняется, если `diagnose` не называет ни одной блокирующей причины: здоровое выполнение отклоняется намеренно. Любой отказ оставляет выполнение нетронутым и называет следующие вызовы. В аудит записываются оба исхода: и восстановление, и отказ. Поверхность продолжения — это то, от чего ещё зависит приостановленный шаг: всё, что объявляет эта нода, кроме того, как она отображается, плюс записи реестра для объявленных ею на вход глобальных переменных. Поэтому обновлённый workflow оставляет приостановленное выполнение пригодным, пока изменение её не затрагивает: новая версия, новые теги, переписанное описание, правка другой ноды или чисто косметическое изменение самой приостановленной ноды пригодность сохраняют.

Ревизия выполнения увеличивается только тогда, когда исходный вызов `step` сохраняет состояние workflow. Изменения родителя, напоминаний, заметки и runtime-переменных не увеличивают её и не делают текущую попытку шага недействительной. Для записи родителя, напоминаний и runtime-переменных нужны `expectedRevision` и соответствующая непрозрачная ревизия из `execution_context`, `reminders`, `variables` или предыдущего изменения (`expectedParentRevision`, `expectedRemindersRevision` или `expectedContextRevision`). Эти ревизии отдельных целей не дают старому снимку метаданных перезаписать более новый в рамках одной генерации шага. Изменение родителя принимает `"none"` для отсоединения, требует выполняющиеся execution одного владельца и отклоняет циклы. Напоминания не меняют план workflow и не дают полномочий; активные напоминания возвращаются при завершении execution. Запись runtime-переменных по умолчанию запрещена, обязана соответствовать схеме переменной и не продвигает граф. Запись по устаревшей ревизии отклоняется до любых изменений; её `AGENT INSTRUCTIONS` велят перечитать это состояние и повторить вызов с текущими ревизиями, не привлекая пользователя.

Когда `current_step` показывает приостановленную ноду материализации, он возвращает новую команду скачивания архива со сроком пять минут, а не содержимое файлов. Разрешение привязано к текущему пользователю, выполнению, ноде и снимку контекста; повторные загрузки допустимы, только пока выполнение ожидает на этой ноде с тем же контекстом. Выполните или повторите возвращённую команду без изменений, затем завершите ноду значением `null` или `{}`; переход выполнения или изменение его контекста делает URL недействительным. Хост, который не может выполнить команду или обратиться к сети, использует вместо этого `materialize`: тот возвращает те же тела файлов в ответе с теми же привязками и окном, но с меньшим ограничением на суммарный размер, и завершает ноду так же.

Разрешения на изображение прогресса привязаны к владельцу выполнения, версии процесса, ревизии шага, ревизии контекста и нормализованным параметрам рендера. Ошибка рендера или HTTP-доставки не расходует разрешение; успешное завершение ответа расходует его.

### Определения процессов и сверка

`manage` разрешает идентификаторы процессов только в пределах доступа вызывающей стороны. Создание и редактирование валидируют итоговое определение до сохранения. Существующий идентификатор перезаписывается только по явному запросу; редактирование отклоняет пустые изменения, отсутствующие или повторные ноды и невалидный итоговый граф.

Операция `get` возвращает все заданные метаданные процесса, реестр переменных, runtime-политику, представление прогресса, напоминание и структурные сведения. `includeNodes: false` исключает только определения нод, а `includeValidation: false` — только результаты валидации. Используйте `list-nodes` для компактного обзора, `get-nodes` для выбранного набора, `analyze-variables` для анализа переменных всего определения и `set-visibility` для переключения собственного процесса между публичным и приватным режимами.

Поиск нод использует ограниченные RE2-совместимые выражения, если запрос содержит синтаксис регулярного выражения, и переходит к регистронезависимому буквальному поиску для некорректных или неподдерживаемых шаблонов. Клонирование отклоняет отсутствующий источник или повторный целевой идентификатор. Перемещение меняет порядок массива, не переписывая заданные соединения, и отклоняет результат, который перестал проходить валидацию.

Операции с переменными процесса работают с объявленным в определении `variableRegistry`. Создание, просмотр и отзыв общего доступа и приглашений требуют полномочий владельца. Неуспешная мутация возвращает MCP-ошибку без частичного применения изменения.

`reconciliation` разрешает конфликты между предыдущей встроенной версией процесса, текущей версией в базе и входящей версией образа. Статус доступен агентам, но полные состояния кандидатов показываются только администраторам; получение кандидата и разрешение конфликта доступны только администратору. Разрешайте конфликт семантически через Workflow Management Flow, а не механическим слиянием JSON графа.

### Блокировки

`lock` принимает только выполнения текущего пользователя. Статус возвращает активную блокировку, список — публичную историю блокировок, а разблокировка проверяет переданный PIN по активной записи. Для создания через MCP нужен выполняющийся процесс без активной блокировки и корректные Telegram-настройки текущего пользователя. Сгенерированный PIN отправляется только в настроенный chat, а несекретные метаданные возвращаются после успешной доставки. При отсутствующих или некорректных настройках и при ошибке отправки эта попытка не оставляет доступной активной блокировки; MCP-ответы и ошибки никогда не содержат PIN.

Отдельный аутентифицированный Web-маршрут создания блокировки один раз показывает PIN человеку — владельцу выполнения. Этот человеческий ответ недоступен через MCP или output workflow node.

### Настройки и заметки

`settings` читает один точный `key`, одну `category` или полный доступный набор. Не объединяйте `key` и `category` в одном запросе get. Определения включают настройки из базы данных и настройки, объявленные в манифестах установленных расширений. Зашифрованные значения всегда маскируются: для настроек из базы возвращается `[encrypted]`, а для настроек расширений — маска из точек с последними четырьмя символами. Административные значения и определения скрыты от пользователей без прав администратора. Запись требует существующее определение и применяет административные ограничения, объявленный тип, опциональную валидацию по JSON Schema, объявленные минимум и максимум встроенной числовой настройки, шифрование и регистрацию Telegram webhook при сохранении токена бота. Структурированное JSON-значение должно проходить сериализацию и чтение без пропуска или преобразования данных. Значение по умолчанию расширения должно пройти ту же проверку типа и схемы до принятия манифеста. Список возвращает доступные сейчас определения, а не сохранённые значения; удаление расширения скрывает его определения, но сохраняет пользовательские значения для последующей переустановки.

`notes` хранит изолированный по пользователям версионируемый текст. При чтении можно выбрать сохранённую версию; удаление мягкое. Сохранение соблюдает настроенные ограничения размера одной заметки, общего хранилища, числа версий, ключей и тегов. Администраторы могут менять действующие лимиты.

### Playbooks

`playbooks` хранит именованный переиспользуемый текст поведения — стандарт ревью, тон, определение
готовности — в одном месте, а не внутри процессов, которые на него опираются: текст правится один
раз, и агент читает его там, где он нужен.

Имя состоит из строчных букв, цифр и дефисов и уникально внутри аккаунта; запись под именем, которое
занято у другого пользователя, создаёт собственный playbook, а не меняет чужой. Каждое сохранение пишет ревизию, `restore` пишет новую ревизию с прежним
текстом, а `compare` показывает разницу двух ревизий построчно. Ревизии хранятся в пределах
настроенного удержания, размер playbook ограничен.

`visibility` публикует playbook или снова делает его приватным. Опубликованный playbook читает любой
аутентифицированный пользователь, назвав владельца, а менять его может только владелец: публикация
отдаёт текст, а не управление им. Чтобы прочитать чужой опубликованный playbook, владельца нужно
назвать через `owner` — по handle или по идентификатору пользователя.

### Публичные артефакты и файлы процессов

`artifacts` управляет публичными статическими HTML-результатами с пользовательскими квотами количества и объёма, ограничением размера файла и сроком хранения. Загрузку можно связать с выполнением; обновление и удаление требуют владения. Операция токена создаёт одноразовое HTTP-разрешение для внешнего клиента загрузки. Администраторы могут менять действующие квоты глобально или для пользователя.

`token` предназначен только для файлового импорта и экспорта процессов. Разрешение загрузки принимает JSON-файл процесса как multipart-поле `workflow`; разрешение скачивания требует доступный процесс. Оба имеют короткий срок действия. Для обычного просмотра и изменения процесса используйте `manage`.

Получив разрешение загрузки от `token`, отправьте выбранный файл на его `uploadUrl`:

```bash
curl -X POST "${uploadUrl}" -F "workflow=@your-workflow.json"
```

### Облачные кодспейсы

Инструмент `codespace` даёт агенту без собственной файловой системы постоянный личный инструмент
для выполнения flow (сейчас — GitHub Codespace). Кодспейс не бывает общим: совместная работа идёт
через ветки системы контроля версий. Весь набор операций обслуживает один инструмент: `action`
выбирает операцию — `list`, `setup_help`, `create`, `get`,
`start`, `stop`, `delete`, `exec`, `stat`, `search`, `read`, `write`, `apply_patch`, `upload` или
`download`, — а остальные поля принадлежат выбранному действию. GitHub подключается только на сайте
Moira; ни одно действие не запускает, не продолжает и не опрашивает авторизацию. Если подключение,
установка приложения или конфигурация сервера отсутствуют, отказ содержит применимый набор
настроенных ссылок активного провайдера. `setup_help` возвращает текущее недостающее условие,
инструкцию провайдера и те же доступные ссылки, включая создание репозитория и, когда URL настроен,
установку приложения; до исправления настройки ничего не создаётся.

Каждый вызов, кроме `list`, `setup_help` и `create`, указывает `codespace_id`; `list` и `create`
возвращают этот переиспользуемый ID, а `setup_help` в нём не нуждается. Владение проверяется на
сервере, поэтому неизвестный или чужой ID возвращает общий результат `CODESPACE_NOT_FOUND`.
Кодспейс не привязан к чату или сессии: используйте один `codespace_id`
из любого клиента. `list` предлагает только кодспейсы, которыми ещё можно
пользоваться: удалённого или отклонённого в списке нет, но `get` по-прежнему отвечает по
его `codespace_id`. `stop` сохраняет данные репозитория (`data_preserved: true`);
`delete` разрушителен и требует `confirm_delete: true` вместе с текущим `generation`
кодспейса, поэтому устаревший вызов не удалит изменившийся кодспейс.

`list` обновляет снимок установок и разрешённых репозиториев после TTL; `refresh: true` запускает
обновление сразу. Если провайдер недоступен, сохранённый список всё равно возвращается с
`repositories_stale: true`. Поэтому новый репозиторий, добавленный в установку приложения, появляется
без повторного подключения, как только обновление проходит успешно.

`list` также возвращает `limits` — пределы, которые Moira применяет к вам, рядом с текущим
использованием. Сюда входят кодспейсы, которые вы держите, относительно вашего собственного предела и
предела всего экземпляра, а также интервал между созданиями; самая большая машина, которую можно
выбрать; ваши активные операции относительно предела конкурентности вместе с пределами ввода,
вывода, сохраняемого вывода, длительности и фоновых команд; ваши байты и объекты передач
относительно их пределов, байты передач, которые ещё в пути, относительно предела для них,
наибольший файл и время жизни ссылки; срок хранения остановленных
кодспейсов, ожидание запуска и ваша настройка автоприостановки вместе с максимальным тайм-аутом
простоя GitHub. Биллинг провайдера сообщается как `unavailable`, потому что GitHub не раскрывает
Moira вашу квоту и биллинг Codespaces. Список кодспейсов на сайте возвращает те же пределы.

Переименование репозитория у провайдера не делает его кодспейс непригодным: идентичность определяется
ID репозитория провайдера, а отображаемое имя обновляется во время lifecycle-операций. Другой ID
репозитория по-прежнему отклоняется.

Ветка, на которой находится кодспейс, не входит в его идентичность. Внутри кодспейса можно
переключать ветки или оставить его на detached HEAD, и `start`, `stop`, `delete`, `exec` и файловые
действия продолжают работать с тем же `codespace_id`; после повторного подключения GitHub тем же
аккаунтом кодспейс автоматически привязывается заново, на какой бы ветке он ни был. Сводка кодспейса
сообщает `requested_ref` — ref, на котором кодспейс создан, — и `current_ref` — ref, который GitHub
последним сообщил как текущий; он равен `null`, пока Moira его не наблюдала и пока кодспейс на
detached HEAD. `create` по-прежнему принимает входное поле `ref`. Запуск кодспейса, ресурс GitHub
которого Moira ещё определяет, возвращает `CODESPACE_CREATE_PENDING` с возможностью повтора;
повторите запуск, когда создание завершится.

Простаивающий кодспейс приостанавливается сам. Когда именно, решают две пользовательские настройки:
`codespaces.auto_stop_enabled` (по умолчанию включена) и `codespaces.idle_timeout_minutes`
(по умолчанию 30, от 5 до 240); их читает и записывает инструмент `settings`. Пока приостановка
включена, Moira останавливает кодспейс, которым столько времени не пользовался ни один агент через
Moira: ни команды, ни файлового действия, ни передачи, ни запуска, — и не останавливает его, пока
там выполняется команда, в том числе фоновая. Остановка сохраняет данные репозитория, а следующий
вызов, которому нужен кодспейс, снова его запускает. Moira не видит прямую работу в браузере,
редакторе или по SSH, поэтому кодспейс, в котором вы работаете напрямую, приостанавливается по тому
же тайм-ауту; если вы работаете в кодспейсах напрямую, выключите приостановку. Независимо от этого
GitHub останавливает кодспейс не позже чем через 240 минут без действий пользователя или терминала,
при включённой или выключенной приостановке, и это может прервать и фоновую команду, которая всё это
время ничего не выводит.

`exec` выполняет argv как данные (без интерполяции в оболочку) в `cwd` относительно
репозитория с необязательным таймаутом (`timeout_seconds`) и необязательными лимитами на каждый
поток вывода и возвращает ограниченные
`stdout`, `stderr` и точный `exit_code`. Эти лимиты ограничивают ответ, а не команду: команда,
напечатавшая больше, продолжает работать, сохраняет собственный код возврата и собственный
`stderr`, а результат сообщает полный размер каждого потока и был ли ответ усечён. Весь вывод
остаётся в кодспейсе до очистки операции, и любой его диапазон читается действием `read`.
Команда останавливается из-за объёма только тогда, когда её сохранённый вывод достигает предела
кодспейса; это сообщается именно так, а не как собственный сбой команды. Для работы, которая
переживает один запрос, например полной сборки или прогона тестов, передайте `background: true`:
вызов сразу возвращает выполняющуюся операцию, команда продолжает работать в кодспейсе под
значительно большим пределом, её вывод читается диапазонами прямо во время работы, а результат
забирается позже по тому же `operation_id` и остаётся доступным не меньше, чем команде было
позволено выполняться. Если `timeout_seconds` не указан, обычная команда получает 300 секунд, а
фоновая — весь свой предел.

Последовательные команды могут работать в общем контексте. Откройте сессию через `session` и
`session_start: true`, затем называйте ту же `session` в последующих командах: она запоминает `cwd`,
указанный вызовом, и переменные, переданные в `env`, и применяет их к каждой продолжающей команде.
Команда без сессии работает как прежде. Внутри сессии вместо `argv` можно передать `script`: он
выполняется оболочкой самого кодспейса, а каталог, в котором он завершился, и переменные, которые
он добавил, изменил или удалил, переносятся в следующие команды — так переживает активация
инструментария или виртуального окружения. Команда `argv` никогда не выполняется через оболочку, и
один вызов несёт одну форму работы. Завершить сессию можно параметром `session_end: true`, отдельно
или вместе с командой; завершение освобождает её место и удаляет сохранённое. Число одновременно открытых сессий в кодспейсе ограничено: когда предел достигнут, следующий
`session_start` получает отказ с названным пределом и просьбой завершить одну из сессий, а не
повторять вызов или создавать другой кодспейс. Сохранённый контекст тоже
ограничен: вызов, который его превысит, получает отказ с названным пределом, а скрипт переносит своё конечное состояние
независимо от того, завершился он успешно или с ошибкой; скрипт, чьё состояние не помещается,
завершивший собственную оболочку через `exit` или остановленный, сообщает `session_capture_dropped`,
вместо того чтобы оставить сессию непригодной. Сессия принадлежит текущей жизни кодспейса: после
остановки и запуска обращение к ней возвращает `CODESPACE_SESSION_UNAVAILABLE`, и нужно открыть
новую, как и для сессии, которую никогда не открывали. То, что хранит сессия, остаётся в
кодспейсе и не возвращается. Остановить любую из них можно вызовом с
`codespace_id`, `operation_id` и `cancel: true`. Команда останавливается вместе со своим
кодспейсом, поэтому длинной команде нужен кодспейс, чей срок простоя её переживёт. Уснувший
кодспейс не нужно запускать заранее: вызов, которому он понадобился, сам его запускает и затем
выполняется — в пределах ограниченного ожидания. Если кодспейс не успевает запуститься, вызов
возвращает `CODESPACE_START_TIMEOUT` с названным пределом ожидания и просьбой повторить вызов; а
кодспейс, который запустить невозможно, получает отказ по своему фактическому состоянию. Команда,
под которой кодспейс перезапустился, сообщается как `CODESPACE_OPERATION_INTERRUPTED` с полем
`interrupted_by_restart` у операции, а не как собственный сбой: уже записанные ею файлы на месте,
результата она не дала, и средство от этого — запустить её снова. Передавайте не более одной формы stdin: `stdin_text` для
UTF-8-текста или `stdin_file` для нативной файловой ссылки ChatGPT; байты файла попадают в процесс
без base64 в переписке. Завершившиеся с ошибкой, по таймауту и отменённые команды, а также
отклонённые правки файлов возвращаются как ошибки инструмента, сохраняющие `operation_id` и
доступный вывод. Быстро завершившаяся команда возвращает терминальный результат тем же вызовом,
который её запустил; всё ещё выполняющаяся возвращает нетерминальный `state`, который не является
успехом. Вызовите то же действие повторно только с `codespace_id` и `operation_id`, чтобы
получить сохранённый итог без повторного запуска команды или мутации.

`read` возвращает UTF-8-текст с `offset` и `total_size`, а для файла репозитория ещё и
`sha256`; передавайте `path` для файла либо `operation_id` и `stream` для сохранённого `stdout` или
`stderr` команды, указывая тот кодспейс, которому эта команда принадлежит. Чтение, начинающееся
на конце потока или за ним, возвращает пустой текст и текущий размер потока. `length` по умолчанию
равен 64 КиБ, а `search` по умолчанию возвращает до 100 совпадений в пределах 64 КиБ, так
что вызов только с codespace, путём и запросом полон. Поиск идёт по содержимому репозитория и
пропускает его собственный каталог `.git`, а также отказывает, если корень поиска указан в этом
каталоге или внутри него; файл в нём по-прежнему читается по точному пути. Нетекстовый диапазон возвращает
`CODESPACE_BINARY_READ_REQUIRES_DOWNLOAD`. Вызов, не соответствующий ни одной форме запроса,
возвращает `CODESPACE_REQUEST_INVALID` с именами отсутствующих или неверных полей. `write` атомарно заменяет файл при
предусловии `expected` (`exists`, необязательные `size_bytes` и `sha256`), а `apply_patch`
применяет упорядоченные правки по байтовым смещениям для каждого файла с теми же предусловиями и
возвращает старую/новую версии и сводку без содержимого. `upload` записывает нативную
файловую ссылку по пути; `download` возвращает файл как MCP `resource_link`, одноразовая
HTTPS-ссылка которого истекает автоматически и не повторяется в JSON-результате.

Агент действует как обычный пользователь Codespace с репозиторием, сетью и настроенными секретами
этого окружения. Moira ограничивает собственную конкурентность, размер ввода/вывода, время и квоты и
защищает сервер Moira и других пользователей; она не изолирует кодспейс от агента, которого
авторизовал его владелец. Пользователь может держать несколько кодспейсов одновременно, а отказ в
создании называет тот предел, который его остановил: ваш собственный предел кодспейсов, которые вы
держите, предел всего экземпляра или интервал между созданиями. Остановленные кодспейсы тоже
учитываются в вашем пределе, поэтому, чтобы освободить место, удалите ненужный. Отказ сообщает настроенное значение этого
предела и никогда не называет другого пользователя или его кодспейсы. Когда в создании, запуске,
остановке или удалении отказывает сам GitHub, ошибка говорит именно об этом, а не о внутреннем сбое:
она различает грант, который нужно переавторизовать, запрос, в котором GitHub откажет и при любом
повторе, и недоступность провайдера, которую имеет смысл повторить, — и передаёт собственное
объяснение GitHub одной укороченной строкой. Эта строка отбрасывается целиком, оставляя только
HTTP-статус, если в ней есть что-либо похожее на учётные данные: токен, помеченный секрет, JWT или
URL.

### Runtime-справка

`help` обнаруживает файловые темы в установленном корпусе MCP-справки и перечисляет рядом с ними прямую тему `tools`. Вызовите его без темы, чтобы получить актуальные имена тем и псевдонимы. Несколько запрошенных тем возвращаются вместе с разделителями. Тема `tools` и её псевдоним `tool` отображают тот же типизированный каталог непосредственно из реестра.
