Moira includes workflow templates for common structured tasks. Templates ensure consistent execution quality through domain knowledge, validation loops, and user approval gates.

## Starting a Workflow

```bash
mcp__moira__start({ workflowId: "<workflow-id>" })
```

## Software Development

### software-development-flow

Filesystem-first delivery of a complete software change: source-grounded planning, implementation, tests, applicable permanent documentation, semantic and mechanical validation, user acceptance, and authorized VCS finalization. The flow classifies the cause of every finding, replans invalid or mechanically undecidable criteria, and prevents supporting validation from becoming a second product.

```mermaid
flowchart LR
    A[Requirements] --> B[Plan and approve] --> C[Implement unit]
    C --> D[Cheap checks and test adequacy]
    D --> E[Architecture and impact-based validation]
    E --> G[Conditional acceptance and checkpoint]
    G -->|more units| C
    G --> F[Docs, final coverage, and report]
    F --> H[Final acceptance]
    H --> I[Conditional VCS reconciliation]
```

| Feature | Description |
|---------|-------------|
| Durable artifacts | Requirements, plan revisions, implementation evidence, reviews, feedback, and final coverage stay in one correlated workspace |
| Source-grounded planning | Assigned tickets, PRs, specifications, and documents are preserved before requirements are extracted; initial VCS and discovery evidence protects unrelated work |
| Complete implementation units | Each approved unit owns dependencies, tests, applicable permanent docs, and focused evidence |
| Layered review | Test adequacy and project-grounded architecture are judged from the diff and primary sources by the implementing agent; a single delegated reviewer then judges the completed unit for completeness and quality, and never re-runs linters, type checks or suites |
| Agent-triggered replan | A teleport entry lets the agent restart planning the moment the plan itself is wrong, instead of waiting for a gate to notice |
| Cause-aware repair | Every finding is classified as a product, test/validation, evidence, documentation/process, or upstream plan/criterion defect before mutation; only the owning artifact is repaired |
| Decidable acceptance evidence | A planned check must distinguish the required state from a plausible wrong state; semantic completeness, architecture, and business provenance remain review judgments when no reliable mechanical observation exists |
| Meta-validation stop | Repeated same-root findings or validation-only changes while product evidence stays green force reassessment and `replan` instead of another proxy, guard, harness, metatest, or proof layer |
| Bounded class-wide repair | A confirmed root is repaired across its real manifestations inside the original task, without inventing a universal scanner for a contextual property |
| Impact-based validation | Runtime, browser, security, performance, broad builds, and full suites run only when project policy or actual risk makes them applicable |
| Mutation-aware cycles | Verification-only repairs rerun cheap checks, test adequacy, and the affected downstream gates while retaining current architecture evidence; any product or test-intent change advances the product iteration and reruns architecture and the full validation suffix |
| Conditional visual evidence | A plan unit explicitly opts into screenshot inspection and a portable self-contained HTML report; incidental UI changes do not enable it automatically |
| Incremental history | With approved VCS authority, each accepted unit checkpoints only its own changes before the next unit starts; unrelated work and workflow artifacts are excluded |
| Explicit authority | Checkpoints and final project-native VCS reconciliation are conditional; final user acceptance occurs before reconciliation, and tool availability never authorizes a side effect |
| Operating mode | The first step resolves `autonomous` or `interactive`. Autonomous runs skip the requirements, plan, unit, and feature approvals and deliver the final report instead; independent reviews, validation gates, and VCS authority are unchanged, and external blockers are decided on re-checked evidence rather than by waiting for a person |

**Use for:** Feature development, bug fixes, code tasks requiring structured planning and validation.

```bash
mcp__moira__start({ workflowId: "moira/software-development-flow", parentExecutionId: "none" })
```

### software-development-flow-lite

Fast complete delivery for one bounded low-risk software change. Lite uses risk-based eligibility, repository-grounded reviewed planning, one complete producer plus a fresh completion pass, applicable deterministic evidence, independent whole-result review, cause-owned repair or reassessment, and authority-bound local VCS closure.

```mermaid
flowchart LR
    A[Eligibility] --> B[Reviewed plan] --> C[Complete production] --> D[Completion pass]
    D --> E[Applicable checks] --> F[Independent review] --> G[Authorized local closure]
    A -. spreading or high-risk .-> H[Full-SDF handoff]
```

| Feature | Description |
|---------|-------------|
| Risk-based Lite boundary | One coherent low-risk outcome; security, data, breaking-contract, multi-unit, rollout-heavy, or uncertain work hands off to full SDF |
| Complete producer ownership | Applicable code, tests, documentation, schemas, generated output, compatibility, and integrations are completed together |
| Matching evidence | Project checks prove measured properties; independent review owns semantic and architectural judgment |
| Cause-aware convergence | Product and verification repair, contract reassessment, handoff, blocked, and abort remain distinct |

**Use for:** One bounded low-risk feature or bug fix with known architecture and a contained recovery surface. Choose full SDF by risk and spread, not by a fixed file or step count.

```bash
mcp__moira__start({ workflowId: "moira/software-development-flow-lite", parentExecutionId: "none" })
```

## Task Management

### quick-task (Recommended)

Filesystem-backed execution for a bounded non-development plan of 1-10 meaningful work units.

```mermaid
flowchart LR
    A[Understand] --> B[Plan] --> C[Approve] --> D[Execute] --> E[Review] --> F[Report]
```

| Feature | Description |
|---------|-------------|
| Durable workspace | Immutable task, plan, review, decision, change, and evidence records |
| Independent gates | Plan review before approval and result review after execution |
| Minimal context | Typed file references, plan length, cursor, and routing values only |

**Use for:** Bounded multi-step non-development tasks executed by an agent with filesystem access. For software implementation, use Software Development Flow Lite or the full Software Development Flow according to risk and spread.

```bash
mcp__moira__start({ workflowId: "moira/quick-task", parentExecutionId: "none" })
```

[See details →](/docs/reference/workflows/quick-task/)

### robust-task

Durable execution of complex, critical tasks with cause-aware independent review and bounded recovery.

```mermaid
flowchart LR
    A[Freeze requirements] --> B[Plan and review] --> C[Execute a complete step] --> D[Classify and repair or replan] --> E[Independent final review] --> F[Truthful delivery]
```

| Feature | Description |
|---------|-------------|
| Durable workspace | Frozen requirements, immutable plan versions, attempt evidence, reviews, decisions, and delivery stay under `./moira-ws/` |
| Cause-aware independent gates | Plan, step, and final reviewers classify the earliest cause as pass, local repair, or replan instead of asking the producer to validate itself |
| Repair ownership | Result repair spends retry budget only after substantive change; evidence/projection repair preserves the correct result; reassessment returns upstream causes to planning |
| Source-pure replanning | Direct review findings and repair-owner reassessments use separate current-cause paths, so stale historical output cannot select a later replan |
| Bounded recovery | Review and result-retry budgets end in a justified repair, replan, or explicit incomplete outcome, never silent success |
| Truthful delivery | End returns the workspace, delivery file, complete/incomplete status, and concise summary |

**Use for:** Complex multi-step work that must survive context loss and retain per-attempt evidence.

```bash
mcp__moira__start({ workflowId: "moira/robust-task", parentExecutionId: "none" })
```

### ux-design

Execution-bound UX/UI specification with traceable decisions, accessibility intent, independent
review, and changed repair.

```mermaid
flowchart LR
    A[Contract] --> B[Package and validation plan] --> C[Independent review]
    C -->|findings| D[Repair earliest source]
    D --> C
    C -->|zero| E[Accept or autonomous delivery]
```

| Feature | Description |
|---------|-------------|
| Durable workspace | Contract, design package, future validation plan, review, and repair account are tied to the current execution |
| Complete design scope | Users, jobs, pains, constraints, applicable states, flows, layout, microcopy, responsive behavior, accessibility intent, risks, and handoff |
| Reuse and rationale | Existing primitives are preferred; every new component requires evidence, alternatives, and integration consequences |
| Independent gate | The same separate reviewer must report exactly zero current blockers after every change |
| Honest boundary | Produces a specification and plan; it does not implement UI, run research, certify WCAG, publish, or deploy |

```bash
mcp__moira__start({ workflowId: "moira/ux-design", parentExecutionId: "none" })
```

## Meta

### workflow-management-flow

Workflow creation, editing, review, and optional publication.

```mermaid
flowchart LR
    A[Start] --> B{Action}
    B -->|create| C[Design]
    B -->|edit| D[Load source]
    D --> E{Full anti-pattern audit?}
    E -->|yes| F[Audit and choose scope]
    E -->|no| G[Analyze and plan]
    F --> G
    C --> H[Design contract]
    H --> J[Independent design review]
    G --> J
    J -->|create repair| H
    J -->|edit repair| G
    J -->|create replan| H
    J -->|edit replan| G
    J -->|pass| K[Optional user approval]
    K --> L[Build and validate]
    L --> M[Independent artifact review]
    M -->|repair| P[Repair artifact]
    P --> M
    M -->|create replan| H
    M -->|edit replan| G
    M -->|pass| N[User report or review]
    N --> O{Publish?}
```

<Aside type="tip">
Use this workflow to create custom workflows or modify existing templates.
</Aside>

| Feature | Description |
|---------|-------------|
| Disk-backed artifacts | Requirements, plans, and review reports stay in the workspace; the analysis of an edit is the first section of its plan, so a correction cannot land in one document and leave a second one stating the superseded version |
| Embedded authoring reference | Engine rules, patterns, anti-patterns, review criteria, cost ordering, and authority rules are shipped inside the workflow |
| Identity-aware editing | The edit path reconciles local and server provenance before semantic planning |
| Optional source audit | Interactive mode asks for consent; autonomous mode chooses from the requested change and available evidence |
| Evidence-aware design | Every proposed proof must distinguish the required state from a plausible wrong state using an appropriate evidence method |
| Pre-mutation design review | Create and edit share an independent semantic gate before artifact mutation; human approval remains a separate decision |
| Criteria fixed by review | Once the edit contract passes independent review, its acceptance criteria are a contract the executor may not reword: a criterion that turns out wrong is taken to the process-revision teleport, where the change is visible, instead of being relaxed in place |
| Cause-aware review | Reviews route to pass, artifact repair, or contract replan; repeated same-root findings without stronger evidence cannot grow another validator layer |
| Bounded class-wide repair | A confirmed root is repaired across its real manifestations in the agreed scope, not converted into a universal contextual detector |
| Validation | The creating or editing node runs the official schema and graph validator |
| Context-aware handoff | Stable file paths are referenced without forcing unchanged rereads or copying file bodies through workflow state |
| Publication gate | Standard, copy-new, and admin-override semantics require an explicit user decision; a real local target is synchronized separately |

```bash
mcp__moira__start({ workflowId: "workflow-management-flow" })
```
