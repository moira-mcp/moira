Moira exposes workflow execution capabilities through MCP tools. The catalog below is the authoritative reference for tool names, actions, input schemas, and valid example inputs. The documentation build reads the same pure typed contract used by MCP registration and runtime help directly.

Tool descriptions and their supported agent/model variants are static parts of this catalog and
cannot be overridden through database settings. Runtime system instructions are delivered separately
through MCP initialization and never alter a tool description.

The server checks the tool-contract revision accepted by the authenticated MCP connection.
HTTP 426 `upgrade_required` requires reconnecting or reinitializing that connection to refresh
its tools. Successful MCP initialization accepts the current catalog for that credential;
reading help or calling an old tool does not bypass the check.

## Behavioral guidance

The catalog defines accepted inputs. These topic owners explain authority, durable state and effects that a schema alone cannot establish.

### User communication

`communication_send` uses the authenticated user's configured channels; callers do not supply recipient credentials or arbitrary headers. Provider limits apply (ordinary Telegram text: 4096 characters).

For `communication_deliver`, pass the host's native file descriptor and metadata unchanged. An explicitly selected registered controller is never replaced because another is available. `communication_deliver_publication` addresses the owner through an existing immutable publication. Publication does not send a message; delivery neither consumes nor renews it. Reads remain subject to expiry and current authority.

The owner retains bytes and the original receipt. Cloud Moira authorizes the channel and streams to its fixed vendor transport without retaining a native-file copy. The owner validates the complete file/text plan before staging; unsupported explicit kinds are refused, not silently changed. Collect the returned original operation with `operation_get`. If its first reply was lost, find candidates at that owner and choose the original explicitly, even for one match. Absence or an unavailable observation does not establish that delivery never happened. See [delivery recovery](/docs/integration/troubleshooting/).

### Workspace purposes and references

Discovery returns opaque workspace, controller, target and installation references. Copy them unchanged; an address is not authority. Lifecycle conflicts require a fresh observation and deliberate decision, including renewed confirmation for deletion.

Commands use argv or script; native stdin requires `command_run_native`. Each deliberate uncontrolled call is a distinct intent: command text cannot deduplicate a lost first reply. Collect original operations/processes through their returned references. Known uncertain outcomes project as `unconfirmed`; a confirmed refusal is completed with `outcome.ok:false`. Neither permits automatic replay or changes the retained receipt. `operation_resume` continues only the original retained private-repository setup, not commands or replacement repositories.

File reads return complete UTF-8 characters and checked references/cursors. Create requires absence; replacement checks complete expected text or an observed reference; patches match text against one original without caller-computed offsets or hashes. Upload needs a native descriptor and explicit create/checked replacement target. Download publishes the complete file, not just an observed prefix. Observation windows do not impose a command deadline. See [workspace and file troubleshooting](/docs/integration/troubleshooting/) and [workspace patterns](/docs/patterns/workspace/).

### Workflow discovery and execution

Follow the [Agent Guide](/docs/integration/agent-guide/) for prepare/execute, current Step attempt identity, exact replay, stale reconciliation, input schema and metadata revisions. Use [Troubleshooting](/docs/integration/troubleshooting/) for diagnose/recover; recovery cannot replay effects, reopen a terminal run or bypass a healthy execution's step.

A step response is evidence of stored execution state, not proof that the agent performed its directive. A missing value, an empty value and a rejected answer are distinct. Materialize archive custody, owner collection, fallback and completion are specified in [Materialize](/docs/reference/materialize/). Task names and one-use progress image grants are specified in [Workflows](/docs/concepts/workflows/).

### Stopping an execution

Use the Agent Guide's [guarded stop operation](/docs/integration/agent-guide/#stopping-a-workflow) for cancellation of a running workflow. It records a permanent stopped result, not successful completion, and does not stop active child runs. `cancel-execution` is for a blocked start; it is not a substitute for stopping a running execution.

### Workflow definitions and reconciliation

The Agent Guide owns [definition reads and mutations](/docs/integration/agent-guide/#reading-and-changing-definitions), pagination and administrator reconciliation. Definition mutation is not workflow execution. Use [Workflow Management Flow](/docs/reference/workflows/workflow-management-flow/) for semantic authoring and conflict resolution.

### Locks

A MCP lock belongs to the current user and requires a running execution and trusted Telegram delivery. No skip flag bypasses PIN delivery; failed delivery leaves no usable active lock. MCP responses never disclose the PIN. The separate authenticated Web creation response shows it once to the owner. See [lock nodes](/docs/concepts/nodes/#lock-node).

### Settings and notes

The Agent Guide owns [setting selectors, masking and validation](/docs/integration/agent-guide/#settings). Masked secrets are not replacement values. [Notes](/docs/concepts/notes/) owns versioned user-scoped text, soft deletion and configurable storage/version/key/tag limits.

### Playbooks

[Playbooks](/docs/concepts/playbooks/) are named reusable behavioral text. Publication grants authenticated reading of the owner's text, not mutation rights. Names are scoped to an account; saving or restoring creates a revision subject to configured retention and size limits. Name another owner's handle or ID explicitly when reading their public playbook.

### Public artifacts and workflow files

[Artifacts](/docs/concepts/artifacts/) owns public static HTML, upload grants, expiry, user quotas and ownership. Use `token` only for short-lived workflow JSON import/export grants; multipart upload uses field `workflow`. Ordinary workflow inspection and mutation use `manage`.

### Development codespaces

Choose one provider for discovery; unrelated providers or billing must not delay it. Use returned references and current permissions for lifecycle operations, repository admission and Git authority. Never substitute a reachable controller for the selected registered owner. Idle/provider limits and provider diagnostics are explained in [Self-hosting](/docs/getting-started/self-hosting/) and [Troubleshooting](/docs/integration/troubleshooting/).

#### Direct guest terminal access

Use the supported guest CLI for an authorized codespace. Preserve full operation output and daemon diagnostics rather than inferring success from a shell exit or the existence of a workspace. `resume_setup` continues the same proven guest lifetime; it does not authorize VM replacement. See [Troubleshooting](/docs/integration/troubleshooting/).

### Runtime help

`help()` discovers English topics and aliases; `help({ topic: "tools" })` renders this same typed catalog. It is not a reader of effective database-overridden system instructions. See [Agent Instructions](/docs/integration/agent-instructions/) for the canonical file default.
