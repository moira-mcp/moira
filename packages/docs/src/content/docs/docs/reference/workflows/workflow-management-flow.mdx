title: Workflow Management Flow
description: Durable evidence-aware workflow authoring with optional static progress design and independent design and artifact review.
---

Workflow Management Flow creates a new Moira workflow or edits one complete existing definition through source preparation, requirements, design, official tooling, independent review, and explicitly authorized publication.

```bash
mcp__moira__start({
  action: "prepare",
  workflowId: "moira/workflow-management-flow",
  parentExecutionId: "none"
})
mcp__moira__start({ action: "execute", startAttemptId: "<Start attempt ID from prepare>" })
```

## Authoring lifecycle

The flow resolves create/edit identity, online or offline source boundaries, a local source hint, and autonomous or interactive mode. It materializes an execution-correlated workspace with the current authoring reference, obtains complete server and repository candidates, records provenance and semantic differences, and never mechanically merges JSON.

Requirements and an optional full antipattern audit feed one outcome-oriented design contract. Independent pre-mutation review must pass before the official workflow CLI changes the complete artifact. The result is validated and rendered through the official structural schema projection, then independently reviewed against the complete JSON, requirements, design, authority, and evidence modalities.

For a workflow with meaningful user-visible stages, the same design lifecycle designs its process view: a short chain of blocks in process order, each with a one-sentence description, every node of the graph — routing nodes included — owned by one block, every edge that leaves a block labelled with the decision it represents, every return explaining its cause and exit, and hubs placed after the blocks that lead into them. WMF's design gate specifies this as part of the pre-mutation contract, its build gates author it with the official CLI and complete only when `derive` reports no diagnostic, and its reviews judge that labels, cycle explanations, descriptions and order are true to the graph. Execution conditions and routes remain in the primary workflow graph; a run is shown from its recorded route. One shared projection and visual model drives both the interface and the server-rendered PNG. Agents may request a short-lived one-time PNG download, while an authorized Telegram node attaches the image directly without storing that token in workflow state. WMF omits progress when it would be decorative.

When one block represents several current roles, WMF may design `progressActiveLabel` on its
waiting nodes. It appears only for the exact current primary node; inactive blocks retain their
stable base label. WMF requires every referenced variable to be authoritative on every route that
can reach that node and rejects stale counters, wrong scope, and progress-owned state or routing.

Artifact-owned findings repair the workflow and repeat stale gates. Invalid criteria or upstream process defects replan. The final report describes exact starts, teleports, terminals, routes, cycles, reachability, coverage, data flow, and every frozen semantic guarantee.

## Publication and local synchronization

Server upload is a separate decision: standard, copy-new, or explicitly authorized admin override. Autonomous mode never invents upload authority. Repository synchronization preserves the resolved target identity and writes no unrelated path. WMF authors the workflow definition; it does not execute the downstream task that workflow will later perform.
