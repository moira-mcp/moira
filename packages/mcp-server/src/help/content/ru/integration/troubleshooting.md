Это руководство помогает восстановиться после типичных проблем при работе с MCP Moira workflows.

## Восстановление контекста после архивации

Когда беседа архивируется или компактируется, агент теряет:

- Текущий execution ID (processId)
- Контекст шага workflow
- Информацию о прогрессе

Состояние workflow сохраняется на MCP сервере - теряется только память агента.

### Шаги восстановления

1. **Найти активные executions:**

```json
session({ action: "executions" })
```

Возвращает список executions со статусом, workflow ID и заметками:

```json
[
  {
    "executionId": "abc-123",
    "workflowId": "development-flow",
    "status": "waiting",
    "note": "Фича: система авторизации",
    "currentNodeId": "implement-step"
  }
]
```

2. **Получить текущий шаг без продвижения:**

```json
session({ action: "current_step", executionId: "abc-123" })
```

Возвращает текущую директиву и контекст:

```json
{
  "attemptId": "attempt-current",
  "directive": "Реализовать фичу...",
  "completionCondition": "Фича работает и протестирована",
  "inputSchema": { ... }
}
```

3. **Продолжить workflow:**

```json
step({ processId: "abc-123", attemptId: "attempt-current", input: { ... } })
```

### Сохранение Process ID

Для облегчения восстановления сохраняйте process ID в рабочей директории:

```bash
# Создать process-id.txt в директории фичи
echo "abc-123" > ./feature-name/process-id.txt
```

Включайте в архивы сессий:

- Название фичи
- Process ID
- Описание текущего шага

## Справочник инструментов навигации

### session - executions

Список всех активных workflow executions текущего пользователя.

**Вызов:** `session({ action: "executions" })`

**Фильтры:**

- `status`: Массив статусов - `["waiting", "running", "completed", "failed"]`
- `workflowId`: Фильтр по конкретному workflow
- `search`: Поиск в заметках executions

**Пример с фильтрами:**

```json
session({
  action: "executions",
  status: ["waiting", "running"],
  search: "auth"
})
```

### session - current_step

Получает текущую директиву шага без продвижения workflow.

**Вызов:** `session({ action: "current_step", executionId: "..." })`

**Параметры:**

- `executionId` (обязательно): ID execution для проверки

**Возвращает:**

- `attemptId`: Идентификатор для отправки именно этого текущего предъявления
- `directive`: Что делать
- `completionCondition`: Критерии успеха
- `inputSchema`: Структура ответа

### session - execution_context

Получает полное состояние execution включая переменные контекста.

**Вызов:** `session({ action: "execution_context", executionId: "..." })`

**Параметры:**

- `executionId` (обязательно): ID execution для просмотра

**Возвращает:**

- `executionId`: UUID execution
- `workflowId`: Выполняемый workflow
- `status`: Статус execution (running, waiting, completed, failed)
- `currentNodeId`: ID текущего узла
- `waitingForInputNodeId`: Узел ожидающий input (если есть)
- `taskTitle`: Каноническое название задачи, отдельное от произвольной заметки
- `taskIdentity`: Сохранённые `{ title, changedAt, changeId }` или `null`
- `revision`, `metadataRevisions.taskIdentity`: Ревизии шага и независимого названия
- `note`: Произвольная заметка execution
- `context.variables`: Переменные контекста
- `context.nodeStates`: Состояния узлов
- `createdAt`, `updatedAt`, `completedAt`: Временные метки
- `error`: Сообщение об ошибке (если failed)

## Типичные проблемы

### "Process not found or expired"

**Причина:** Неверный или истёкший processId

**Решение:**

1. Используйте `session({ action: "executions" })` для поиска активных executions
2. Используйте правильный executionId из списка
3. Process ID - это UUID типа `abc123-def456-...`

### "Execution is not waiting for input"

**Причина:** Попытка продвинуть завершённый или упавший execution

**Решение:**

1. Проверьте статус execution через `session({ action: "execution_context", executionId: "..." })`
2. Статус должен быть `waiting` для принятия input
3. Если `completed` или `failed`, запустите новый execution

### Ошибки валидации на step()

**Причина:** Input не соответствует inputSchema

**Решение:**

1. Проверьте `inputSchema` текущего шага
2. Убедитесь что имена полей совпадают точно (регистрозависимо)
3. Убедитесь что типы данных совпадают (string vs number)
4. Включите все обязательные поля

### `ATTEMPT_PROCESSING`

**Причина:** Другой вызывающий всё ещё владеет активной заявкой на изменение именно этого шага.

**Решение:** Повторите вызов с теми же Process ID, идентификатором попытки и входными данными. Не
заменяйте попытку и не изменяйте ввод.

### `ATTEMPT_STALE`

**Причина:** Попытка больше не соответствует текущему предъявлению execution и была отклонена до
работы обработчика.

**Решение:** Автоматически вызовите `session({ action: "current_step", executionId: "..." })`, затем
один раз повторите исходную отправку с возвращённым идентификатором попытки. Не используйте
устаревший идентификатор повторно.

### `ATTEMPT_CONFLICT`

**Причина:** Попытка уже связана с другими входными данными, поэтому новая отправка отклонена до
работы обработчика.

**Решение:** Автоматически вызовите `session({ action: "current_step", executionId: "..." })`,
отбросьте конфликтующую попытку и продолжите по возвращённой директиве и входной схеме. Не
повторяйте отклонённый ввод для текущего предъявления.

### `ATTEMPT_INVALID_OR_EXPIRED` для шага

**Причина:** Попытка шага недоступна и отклонена до работы обработчика. Это восстановление
применимо, только если ошибка явно предписывает прочитать `current_step`: у недоступной попытки
запуска нет текущего шага для восстановления.

**Решение:** Автоматически вызовите `session({ action: "current_step", executionId: "..." })`,
отбросьте недоступную попытку и продолжите по возвращённой директиве и входной схеме.

### `ATTEMPT_OUTCOME_UNKNOWN`

**Причина:** Moira не может доказать, завершилось ли уже принятое изменение и связанный с ним
возможный внешний эффект.

**Решение:** Изучите выполнение через `session({ action: "current_step", executionId: "..." })` и
состояние соответствующей внешней системы. Не повторяйте изменение автоматически.

### `CURRENT_PRESENTATION_STALE`

**Причина:** Сохранённая живая попытка относится к другой ноде или к поверхности продолжения,
которой в текущем определении больше нет: изменилось что-то из того, что приостановленная нода
объявляет о своей работе, либо изменилась запись реестра для объявленной ею на вход глобальной
переменной. Безопасно перепривязать такую попытку к текущему execution нельзя. Изменение, не
затрагивающее эту поверхность, к этому состоянию не приводит: смена версии или тегов, правка другой
ноды и косметическое изменение самой приостановленной ноды пригодность сохраняют.

**Решение:** Не повторяйте старую попытку. Вызовите
`session({ action: 'diagnose', executionId: '...' })`: он назовёт, какие факты приостановленного
шага изменились, сохранилась ли его нода и что ещё стоит между выполнением и следующим шагом. Затем
восстановите выполнение вызовом
`session({ action: 'recover', executionId: '...', nodeId: '<нода для возобновления>', variableValues: { ... } })`:
он предъявит названную вами ноду заново вместе со значениями, которые нужны этому шагу, и вернёт
свежий идентификатор попытки шага для продолжения. Называйте ноду, на которой выполнение может
ожидать: agent-directive, teleport, materialize, lock или subgraph. Любая другая нода отклоняется,
потому что возобновление на ней означало бы прогон workflow вперёд, а не восстановление.
Выполнение останавливается на названной ноде и дальше не идёт, но нода `lock` при появлении
выполнения создаёт блокировку и отправляет код подтверждения, а нода `subgraph` заходит в дочернее
выполнение: выбирайте такую цель, только если этот эффект вам нужен.
Восстановление отклоняется и тогда, когда выполнение и так может продолжиться, и для выполнения,
которое уже завершено или отменено, — таким оно и останется; отказ ничего не меняет.
Для цели materialize восстановление оставляет запуск на паузе на этой ноде. Выполните предъявленную
доставку, чтобы получить текущие файлы справочника; изменение контекста само по себе их не обновляет.

### Устаревшая запись названия задачи

Перечитайте `execution_context` и согласуйте название с фактической задачей, затем повторите
`update-task-title` с текущими ревизиями шага и названия. Возврат к прежнему тексту при том же
времени часов тоже делает старую ревизию недействительной. Не обходите защиту и не используйте
заметку как название; см. [именование задачи](/ru/docs/concepts/workflows/#название-задачи-запуска).

### `STEP_BLOCKED` или `RECOVERY REQUIRED` из-за переменной выражения

**Причина:** Выражению текущей ноды agent-directive нужны сохранённые данные выполнения.
Названной переменной нет, и Moira может установить, что её нельзя передать полем ответа, которое
допускает входная схема и которое нода объявляет выходным. Открытая входная схема не делает
необъявленное поле пригодным для продолжения. Объявленное поле тоже недоступно, когда входная
схема структурно запрещает его, например через `maxProperties: 0`, схему свойства `false` или
запрет внутри `allOf`. Если запрет не доказан, исправьте некорректный ответ обычным повтором.
Такое возможно, если определение workflow меняется во время выполнения. Сама по себе
записанная ошибка относится к истории; продолжение блокирует отсутствие значения в текущем контексте.

**Решение:** Вызовите `session({ action: "diagnose", executionId: "..." })` и найдите блокирующую
причину `missing_expression_variables`. Передайте названные значения через
`session({ action: "recover", executionId: "...", nodeId: "<текущая нода>", variableValues: { ... } })`.
Значения объявленных переменных должны соответствовать схемам реестра; посмотреть объявления можно
через `session({ action: "variables", executionId: "..." })`. Если восстановление отклонило
отсутствующее или некорректное значение, исправьте `variableValues` и повторите вызов: отказ не
изменяет выполнение. После успеха используйте свежий идентификатор попытки и отправьте обычный
ответ на ту же ноду. Не повторяйте прежний ответ, пока не добавлено недостающее сохранённое значение.
Если сначала упало выражение из-за данных текущего ответа, исправьте ответ: `diagnose` при этом
может отдельно назвать более позднее отсутствующее сохранённое значение, требующее восстановления.
Заданный у ноды путь обработки ошибки действует как обычно.

### Агент забывает контекст Workflow

**Причина:** Сессия была архивирована/компактирована

**Решение:**

1. Проверьте process-id.txt в рабочей директории
2. Используйте `session({ action: "current_step" })` для получения контекста
3. Напомните агенту: "Продолжай workflow \{processId\}"

### `[[UNDEFINED_VARIABLE]]` в директиве в рантайме

**Причина:** Используемая переменная не была разрешена при отрисовке директивы. Три причины:

1. Переменная не объявлена в `variableRegistry`.
2. Переменная объявлена, но без `default`, и её не записал вышестоящий узел до того, как директива её использовала.
3. Голый `{{...}}` был помещён в данные, которые агент вернул через `step()`, и эти данные позже подставились в директиву (template-in-data). Возвращаемые значения данных литеральны — они не пересканируются как шаблоны.

Движок логирует предупреждение с указанием оставшегося плейсхолдера и `executionId`.

**Решение:**

1. Объявите переменную в `variableRegistry` со значением `default`.
2. Убедитесь, что вышестоящий узел записывает переменную (через `globalInputs`) до её первого использования.
3. Никогда не подставляйте `{{...}}` в данные, возвращаемые из `step()` — держите шаблоны только в статических полях узла.

### Правка файлов при работающей команде

Работающая команда или сервер разработки сами по себе не блокируют `file_create`, `file_replace`,
`file_patch` и `file_upload`. Для замены передавайте ожидаемый полный текст или возвращённую
файловую ссылку. Если другой автор изменил файл, перечитайте и согласуйте новую явную правку.
Хеш выбранных байтов не заменяет предусловие всего файла. Фиксация и восстановление используют
атомарные транзакции гостя; восстановление не перезаписывает более позднюю правку.

### Большие файлы и отказы файловых операций

Используйте `file_stat` для метаданных и `file_read` с окном строк или возвращённым курсором для
текста. Продолжение сохраняет полные символы UTF-8: кириллица или emoji на внутренней байтовой
границе не делают файл бинарным. `file_download` возвращает полные бинарные байты; имя и MIME
выводятся при отсутствии, предварительный stat не нужен. Допускается пустой файл.
`file_preview` возвращает полный корректный PNG/JPEG, а не SVG или префикс изображения.
Структурная проверка не доказывает запуск браузера или визуальную корректность снимка.
Необязательный `max_bytes` — выбранный предел, а не общая квота передачи.

Действуют место на диске, текущие права, проверки репозитория/пути и ожидаемого содержимого.
Нативный дескриптор передаётся владельцу потоком без base64. Прямой CLI
`~/.local/bin/moira-workspace` использует того же Unix-владельца без облачного соединения;
фиксированный bootstrap обновляет сервис на месте, не заменяя VM и её диски.

`communication_deliver` принимает нативный файл у выбранного контроллера;
`communication_deliver_publication` отправляет собственную `file.reference_id`.
Необязательный `channel` выбирает настроенный канал, но не адресата. Публикация не отправляет
сообщение; доставка не расходует и не продлевает её. Истёкший срок требует отдельной намеренной
публикации. Расширения используют объявленный бинарный транспорт.

Сохраняйте возвращённую `operation`, в том числе в результате workflow-уведомления с вложением.
`operation_get({ reference })` не загружает, не рендерит и не отправляет повторно. Неопределённый
исход владельца публично имеет `unconfirmed`, даже если приватная запись конечная;
подтверждённый отказ остаётся completed с `outcome.ok:false`. Один канал может оставаться
неопределённым после успешного другого. Поиск возвращает ссылки и безопасные метаданные, а не
полные результаты; выбранный исходный результат читайте отдельно. При потере первого ответа
используйте `operation_find` у выбранного владельца и явно выберите кандидата. Даже один кандидат
или отсутствие кандидатов не доказывают, какой эффект произошёл. Не создавайте новую доставку
лишь потому, что исходный результат отсутствует, недоступен или не подтверждён.

При `COMMUNICATION_OWNER_UNAVAILABLE` восстановите выбранный контроллер или гостевой маршрут,
не подменяя владельца. Обычный текст независим. Для materialize-архива HTTP 409
`COMMUNICATION_OUTCOME_UNCONFIRMED` читается по тому же grant URL без повтора и смены владельца.
HTTP 422 сообщает ошибку владельца, HTTP 503 — недоступный контроллер. Не завершайте шаг workflow
без файлов. Новая презентация `current_step` — отдельная явная попытка; текстовый fallback
`session materialize` не требует файлового владельца.

## Подготовка GitHub и удалённая готовность

Состояние провайдера `available`, проверенная готовность локального Unix API и доступный удалённый
маршрут — разные факты. Гостевой CLI может работать до первой регистрации. Удалённым командам и
файлам нужно текущее зарегистрированное соединение; сохранённое наблюдение `running` его не заменяет.

При первоначальном `unconfigured` или `enrollment_unavailable` сначала прочитайте исходную
операцию и подтвердите завершение её scoped SSH-процессов. Если известное окружение GitHub
сохраняет `CODESPACE_LOCAL_SETUP_INCOMPLETE`, восстановите выбранный контроллер и текущий доступ
GitHub, затем выберите **Продолжить подготовку** или вызовите
`workspace_lifecycle({ workspace, action: "resume_setup" })` с возвращённой ссылкой workspace.
Контроллер использует сохранённое исходное доказательство корня/репозитория, времени жизни гостя,
установленного релиза и назначения. Он выполняет фиксированную конфигурацию и регистрацию без
запуска провайдера, установки payload, adopt или другой VM. Отсутствие доказательства либо смена
времени жизни, поколения или прав запрещает продолжение. Чтение результата само не регистрирует
гостя и не открывает SSH.

Уже зарегистрированный гость в `connecting` или `unavailable` использует существующий цикл
подключения; продолжение подготовки не заменяет его права. После настоящей смены времени жизни
при холодном перезапуске сохранённое право продления позволяет открыть Unix API до удалённого
продления. Сетевые ошибки и сбои хранилища повторяют тот же сохранённый запрос продления;
credentials прежней жизни не могут открыть соединение. Подтверждённый отказ требует исправить
права, сохраняя локально разрешённую работу. Никогда не зарегистрированный гость не может
продлевать доступ или создавать новое исходное доказательство после смены времени жизни.
Сохраните его состояние и проверьте исходную операцию через назначенный контроллер.

Последующая регистрация или продление подключается к тому же работающему Unix-владельцу без
повтора команд. Холодный перезапуск может прервать процессы и не обещает непрерывного исполнения.

## Локальные кодспейсы

Используйте `command_run` или `command_run_native` с возвращённой ссылкой workspace.
Адаптер создаёт внутреннюю identity; не составляйте UUID или ID процесса вручную.
Команда может вернуть ответ до завершения. Её `operation` читается через `operation_get`,
а `process` — через `process_output` или явный `process_stop`. Наблюдение не отменяет работу;
ожидающая отмена не доказывает физическую остановку. Намеренно одинаковые команды — разные
намерения. Неконтролируемый первый ответ не имеет гарантии автоматической дедупликации.

Гость хранит подтверждения команд и stdout/stderr. Для получения нужны доступный
сервис и сохранённые гостевые данные; второй копии в облачном хранилище нет.
Отключение облачной связи не отменяет гостевую команду. Остановка VM, idle stop
провайдера или перезагрузка могут её прервать. Отсутствующие и архивные подтверждения
не исполняются повторно. Сохраняйте старые UNKNOWN-записи для диагностики; не переносите
их ID в новую область имён. Явный срок исполнения команды и предел ожидания клиента
независимы.

Маршрутизация workspace для GitHub Codespaces и Local требует доступного, уже подготовленного
и enrolled сервиса владельца. Явно запустите ресурс и завершите подготовку его провайдера перед
workspace-инструментами. Недоступный владелец возвращает `CODESPACE_PROVIDER_UNAVAILABLE`
до отправки операции; маршрутизация не запускает VM и не выполняет облачный bootstrap автоматически.
При недоступном компьютере восстановите соединение companion.
`CODESPACE_PROVIDER_DISABLED` означает выключенную конфигурацию провайдера GitHub.
Local использует права владельца, включённое разрешение и физическую ёмкость вместо облачных
операционных контролей. Для GitHub create/start/adopt восстановите назначенный сопряжённый
контроллер; удалённому доступу к гостю также нужна аутентифицированная исходящая регистрация.
Одна готовность конфигурации `ready` её не доказывает. Подтверждённый отказ регистрации 401/403
требует исправления прав; временная сетевая потеря позволяет переподключить ту же действительную
identity без повторного исполнения исходной операции.

`CODESPACE_AUTHORIZATION_REQUIRED` требует восстановить реальные права аккаунта,
устройства или репозитория в Настройках. Хостовый CLI поддерживает `create OWNER/REPO --ref BRANCH`,
`start WORKSPACE_REF`, `resume-setup WORKSPACE_REF`, `stop WORKSPACE_REF`,
`remove WORKSPACE_REF --confirm`, `collect OPERATION_REF` и `operations CONTROLLER_REF`
через работающий приватный контроллер. Raw execution на хосте не поддерживается.
Привилегированные запросы обслуживания и security сохраняют отдельный
`collect ORIGINAL_REQUEST_ID`; это не отправка lifecycle-запроса по raw ID.
Новое создание требует облачной регистрации и начальных прав Git. Уже допущенные VM
подчиняются текущим локальным правам и офлайн.

Через `workspace_targets` получите выбранный контроллер и ссылки личных installation.
`repository_admit` требует применённого existing-private consent и доступного App репозитория
подключённого личного аккаунта. Он не расширяет права; ожидающая редакция настроек должна сначала
завершиться. `repository_create` требует new-private consent. Organization installations и
публичное создание не поддерживаются.

Сохраните исходную операцию. `operation_get` только читает; после исправления permissions,
installation access или допуска `operation_resume` явно продолжает только исходное создание
приватного репозитория. Он не перезапускает команды и не создаёт замену.
`setup_required` может сохранять подтверждённый репозиторий с незавершённым допуском.
Неизвестное создание проверяет сохранённый marker в description; чужой same-name репозиторий
или отсутствие наблюдения не разрешают неопределённость. Не удаляйте marker до её разрешения.
Отклонённый допуск может оставить репозиторий на GitHub: восстановите grant в Настройках либо
запросите existing-private admission при разрешении владельца. Отказ не разрешает новый create.

Сопоставьте **Настройки → Разработка → Локальные компьютеры** и `status` companion: ожидание
подтверждения браузером, отзыв, недоступность компьютера и выключенную работу — разные
состояния. Недоступная строка не доказывает физическую остановку компьютера или его VM.
Включите работу на компьютере через `npm run local -- enable`; разрешение действует до явного отключения.
`npm run local -- install` сохраняет полный релиз владельца и регистрирует запуск при входе;
`npm run local -- run` запускает владельца или подключается к нему. Постоянный владелец хоста
удерживает VM, брокер и туннель; завершение этого клиента их не останавливает.
Обычная установка сохраняет релиз для обслуживания, не заменяя работающего владельца.
`npm run local -- service-status` показывает работающий релиз, готовность, облачное соединение,
подготовленный релиз и ошибку запуска. Отозванное устройство требует нового сопряжения
и подтверждения браузером.
Откройте карточку кодспейса нужного компьютера и нажмите **Проверить состояние снова**, если
ожидаются запуск, остановка или удаление. Кнопка читает результат исходной операции, если её
ID известен, иначе только обновляет наблюдение. Она не повторяет запуск, остановку или удаление
и не создаёт заменяющую VM. Ошибки и загрузка остаются в этой карточке.
**Удалить** доступно с подтверждением при ожидающем создании, очистке или неопределённом
локальном состоянии, когда текущая сводка содержит возвращённую ссылку workspace.
Недоступные идентичности не имеют lifecycle-кнопок. Удаление адресует то же зафиксированное
наблюдение и завершается после подтверждённого отсутствия. Для ручной очистки нужны активное
сопряжение, web control и доступный владелец, но не право удаления агенту или включённая работа;
она не меняет эти разрешения. Удаление через MCP сохраняет проверки прав агента и включения.

Отказ остаётся в диалоге и завершает индикатор; **Отмена** доступна. Фоновое обновление не
заменяет выбранную цель удаления. После проверки другого наблюдения нужно новое явное
подтверждение; автоматический повтор не должен обновлять предусловия. Отказ операции с кодом
403 не завершает сессию владельца; истёкшая сессия и ограничения аккаунта сохраняют штатную
обработку авторизации. Не удаляйте журналы, не меняйте базу и не создавайте замену для обхода
незавершённого удаления.

`observed_at` в сводке кодспейса — время последнего проверенного наблюдения провайдера, nullable
до первого успешного чтения. `updated_at` — время служебного обновления и не доказывает
свежесть состояния runtime. `lifecycle_error` содержит безопасный код диагностики, а не сырой
ответ провайдера. Отказ адресного наблюдения сохраняет проверенные состояние/время и не доказывает
отсутствие. Исправные соседние VM продолжают обновляться и работать. Физический запуск не означает
завершённую подготовку гостя. Локальная VM в `created` допускает действие, но завершение остановки
требует независимого native settlement; ошибка SDK сама по себе не завершает остановку.
Для create/start/stop/delete передавайте возвращённые target/workspace-ссылки без изменений.
Конфликт требует нового наблюдения и явного решения, а не автоматического повтора с обновлённым
предусловием. `operation_get` читает исходную операцию; `pending_operations` восстанавливает чтение
после перезагрузки. При потере первого ответа доступен `operation_find` у выбранного контроллера
с явным выбором кандидата. `absent` или новые метаданные не разрешают повтор неопределённого изменения.

Облачная регистрация — маршрут, а не наблюдение машины. `workspace_observe` может вернуть
`CODESPACE_PROVIDER_UNAVAILABLE`, не выдумывая состояние или поколение. Для диагностики Local
вызовите `workspace_list({ provider: "local-sandboxes", view: "diagnostics" })`, а для GitHub
выберите `provider: "github-codespaces"`. Обычный список содержит текущие пригодные среды и
известную незавершённую подготовку. Диагностика сохраняет неопределённые или недоступные идентичности,
безопасные ошибки и ссылки исходных операций без поколения для lifecycle. `has_diagnostics`
указывает на сохранённую диагностику; `view: "history"` показывает подтверждённо выведенные из
эксплуатации среды. Отказ выбранного провайдера не доказывает пустой список; Local не ждёт GitHub
или биллинг. В Настройках выберите Диагностику или Историю нужного провайдера; биллинг имеет своё
чтение и повтор в подразделе GitHub.
Неизвестное создание остаётся исходной операцией, а не заменяющей VM. Nullable machine не задаёт
профиль по умолчанию или разрешение запуска.

При `CODESPACE_LOCAL_SETUP_INCOMPLETE` у Local исправьте предпосылку и выберите **Продолжить подготовку**,
`workspace_lifecycle({ workspace, action: "resume_setup" })` или хостовый
`resume-setup WORKSPACE_REF`. Это готовит ту же известную VM, сохраняя файлы и исходный результат
создания. Обычный запуск и custody `recover` настройку не продолжают.
Необязательный `setup_failure` указывает проверку сохранённого корня (`repository_unproven`),
Python3/libc/исключительной публикации (`prerequisite_unavailable`), доступа/ref репозитория
(`repository_checkout_failed`) или диагностики конфигурации (`configuration_failed`).
Неизвестное создание или settlement гостя требует чтения исходного результата, а не принятия VM
по имени. Подтверждение custody владельцем сохраняет незавершённую подготовку; затем явно продолжите её.

При `CODESPACE_LOCAL_PROTOCOL_ERROR` согласуйте сборки сервера/companion и сохраните identity
и журналы. При `CODESPACE_LOCAL_RUNTIME_ERROR` исправьте сам runtime и проверьте тот же workspace;
ошибка не означает остановку. `CODESPACE_LOCAL_DELETE_APPROVAL_REQUIRED` требует подтверждения
в Настройки → Разработка → Локальные компьютеры при действующем web control, а не постоянного
права агента на удаление.

После локального разрешения `web-control` можно запросить настройки в редакторе
устройства в пределах одобренных ресурсов. Ожидание означает, что компьютер ещё
не применил запрос; при отклонении показана причина и сохраняется последняя успешно подтверждённая
редакция. Отказ применения может выключить работу в сообщаемой policy; сама редакция не означает,
что работа остаётся включённой. Недоступный компьютер не предоставляет действующие policy и права.
Сохранение отклоняется, черновик остаётся в редакторе; восстановите связь и обновите состояние
перед явным сохранением. Уже принятый запрос настроек сохраняет исходный ID для чтения результата,
которое не повторяет изменение. Успешный исторический результат может не содержать типизированной
проекции текущего устройства; обновите текущие настройки отдельным чтением, не отправляя изменение
заново. Название, права, автор Git и настройки новых VM применяются без остановки при неизменных
включении и общем хранилище. Принятые профили существующих VM сохраняются; изменение включения
или общего хранилища использует физический переход.
Автор Git меняется в policy; локальная Git-конфигурация репозитория получает это значение при
подготовке workspace. Само сохранение настройки не перезаписывает уже работающий checkout.

Daemon выводит в stderr структурированный статус `connected`, `offline`, `faulted` или `disabled`.
Сетевая ошибка/5xx делает удалённое состояние владельца недоступным, сохраняя принятую работу VM.
Новые удалённые изменения отклоняются, а не ставятся в очередь. Адресный отказ ресурса возвращает
безопасную ошибку этого запроса; потерянный ответ на принятый эффект требует чтения исходного результата.
Отказ авторизации device endpoint или подтверждённый отзыв/смена identity устройства закрывает
удалённый маршрут, не превращая локальное намерение работы VM в остановку.
Локальное отключение и явная физическая остановка действуют независимо.
Текущие права сохраняют силу. Возврат сохранённого результата не повторяет эффект;
недоступная строка не обещает немедленный отзыв на компьютере.

Git и PR напрямую выполняются фиксированным доверенным брокером владельца. Исходные OAuth/refresh
credentials остаются на сервере; производный токен ограничен одобренным репозиторием и действием.
`SCOPED_CREDENTIAL_OUTCOME_UNCONFIRMED`, `SCOPED_CREDENTIAL_CUSTODY_UNCONFIRMED` и
`SCOPED_CREDENTIAL_DISPOSAL_PENDING` требуют чтения исходного `security_request_id`.
На локальном хосте используйте `moira-local status --json` и `moira-local collect ORIGINAL_ID`.
Чтение не выпускает токен, не повторяет Git и не отменяет живую передачу; отсутствие результата
не разрешает автоматический перевыпуск. Отказ issuer не включает переход на токен хоста.

При неизвестном создании PR сохраните операцию и читайте её через `operation_get` или гостевой
`moira-workspace get OPERATION_REF`. `pull_request_read` или `pr-find HEAD BASE` проверяют ту же
пару head/base перед намеренным новым созданием. Не вызывайте `pull_request_create` снова для чтения.
Отказ PR до отправки может сочетаться с неопределённой credential custody; читайте отдельный
привилегированный security-запрос без выпуска другого токена.

Блокировка аккаунта или отзыв прав ресурса могут сохранить ошибку незавершённого отзыва токена
без подтверждения остановки провайдера. Удаление аккаунта возвращает
`ACCOUNT_CREDENTIAL_RETIREMENT_PENDING` либо `ACCOUNT_RESOURCE_RETIREMENT_PENDING`, сохраняя
блокировку и ключи очистки. Явно удалите собственные managed resources существующим подтверждённым
действием очистки перед запросом удаления аккаунта; остановка постоянной VM не удаляет её диск,
и удаление аккаунта не делает этого автоматически.
Отзыв Local устройства или привязки ресурса тоже не подтверждает удаление. Исторический ресурс
без подтверждённого удаления, в том числе без привязки или с неизвестным native-исходом,
сохраняет свидетельство владения и ожидание удаления
аккаунта до подтверждённого окончательного удаления точного ресурса.

HTTP 401/403 при получении Git identity может безопасно направить владельца обновить доступ к
репозиторию, добавить его в installation App либо переподключить проверенную identity GitHub
в Настройках. Другой текст ответа остаётся приватным; отказ не разрешает токен хоста или расширение прав.
Гостевой прокси авторизует запросы пакетов разрешением своего кодспейса;
Клиент пакетов не обязан передавать заголовок proxy-auth. Хост проверяет включённое разрешение работы,
права репозитория, публичность адресов и исключение сетей компьютера. Отказ прокси не разрешает расширять доступ или
использовать токен хоста/GitHub.
Таймауты локального CONNECT ограничивают установление соединения. После подключения к фиксированному
брокеру и проверки подключённого внешнего адреса эти таймауты не задают срок простоя туннеля.
Текущее разрешение, отзыв прав, закрытие сокета и остановка брокера по-прежнему управляют доступом.
Публичные адреса доступны независимо от технологии; у сетевых загрузок нет накопительной квоты
трафика, размера ответа, количества соединений или длительности установленной передачи.
Адреса компьютера, локальной сети и служебных сетей остаются запрещены.

`doctor` требует включённого разрешения и проверяет предпосылки, а не изоляцию live VM.
Ограниченное окно диагностики не подтверждает завершение ожидающей работы. Текущие права проверяются
и во время запуска SDK; установка и регистрация не ограничены общим сроком исполнения работы.
Статусы устройства `active`/`enabled` и настройки `ready` описывают права и конфигурацию, а не
успешное гостевое соединение. Работающий гостевой Unix API готов до необязательного получения
workspace credentials и может оставаться готовым при недоступном удалённом доступе. Ожидание
облачного ответа не удерживает допуск локальной работы или lifecycle; перед применением ответа
повторно проверяются runtime, поколение, права и соединение. Повторная подготовка использует заданные
или точно привязанные сохранённые данные автора; checkout публичного репозитория не зависит от
необязательного запроса Git-автора. Первоначальный private checkout требует текущих прав.
Необязательное наблюдение `remote.state` принимает `unconfigured`,
`enrollment_unavailable`, `connecting`, `connected`, `unavailable` или `refused`; отсутствие
наблюдения остаётся неизвестностью. Недоступная регистрация ожидает восстановления текущего
допуска; существующий недоступный транспорт переподключается с теми же правами. Временный сетевой
сбой или отказ хранилища не означает подтверждённого отзыва. Подтверждённый отказ закрывает эту
удалённую авторизацию, не останавливая локально разрешённую работу. Последующая регистрация обновляет
того же Unix-владельца без повтора принятых команд. При таймаутах проверьте текущую диагностику.
После входа в систему или холодного перезапуска установленный сервис восстанавливает намерение
работы тех же известных VM и дисков при доступных runtime, credentials и действующем разрешении.
`run` запускает владельца или подключается к нему. Старый runner marker восстанавливается только
после подтверждения отсутствия прежних runner и guard под системной блокировкой.
Сохранённая работа остаётся; принятые команды и неизвестные операции не повторяются.
Перезагрузка хоста может прервать команды и требует нового захвата kernel identity;
она не является непрерывным исполнением. Живой или непроверяемый владелец остаётся отказанным; не удаляйте его lock или receipt
ради обхода проверки.
Если после перезагрузки отсутствует стандартная точка монтирования хранилища macOS, проверьте
`service-status` с тем же каталогом состояния. Запуск подключает только существующий собственный
`storage.sparsebundle`, проверяет native-привязку точки монтирования, владельца тома и согласованную
ёмкость без фиксированного запаса свободного места. Потерянный ответ attach разрешается наблюдением этой привязки.
`LOCAL_STORAGE_NOT_MOUNTED` означает, что хранилище остаётся недоступным: пользовательский том
смонтируйте вручную, а для стандартного проверьте наличие и возможность подключения сохранённого
образа. При `LOCAL_STORAGE_OWNER` устраните небезопасный образ/точку монтирования или конфликт
привязки. Сохраните образ и состояние; запуск не создаёт заменяющий диск и не сбрасывает данные
ради обхода отказа.
После исправления предпосылки запуска повторный `run` при доступном endpoint сервиса с ошибкой
только выводит сохранённый статус и не повторяет инициализацию. Если владелец не работает,
`run` запускает выбранного владельца. Если исходный результат обслуживания остаётся в фазе
`selected` для этого работающего релиза, повторите исходное намерение через
`maintenance --request-id ORIGINAL_ID --confirm`;
для исходной паузы используйте `maintenance --resume --request-id ORIGINAL_ID --confirm`.
Это перезапускает владельца с ошибкой запуска без повторения уже подтверждённой физической
остановки или выбора релиза. Продолжайте читать тот же ID: завершение подтверждает только
результат восстановления от преемника.
Другие неподтверждённые фазы обслуживания по-прежнему требуют описанного ниже восстановления
доказательства физической остановки; этот повтор только инициализации к ним не применяется.
Если незавершённого обслуживания нет, явно перезапустите активный релиз через
`maintenance --pause --confirm`, сохраните ID, дождитесь `paused` при чтении результата и выполните
`maintenance --resume --request-id ORIGINAL_ID --confirm`. Для этой паузы не нужен новый
подготовленный релиз; она объявляет физическое прерывание. При необходимости запустите выбранного
владельца через `run`, затем проверьте `service-status` и исходный результат. Во всех командах
используйте тот же `--state PATH`; не меняйте lock или сокеты, не заменяйте сопряжение и не
повторяйте прерванные команды.
Если companion сообщает `LOCAL_STORAGE_FULL` при уменьшении, запрошенный размер не вмещает
существующие данные или меньше native-минимума APFS. Проверьте ёмкость общего дискового образа
компьютера и фактическое место на диске отдельно от свободного места на Mac; допуск не требует
дополнительного запаса. Чтобы повысить одобренный максимум, явно приостановите физического
владельца и сохраните выведенный ID обслуживания. Перед изменением локального одобрения дождитесь
результата `paused` при чтении этого ID:

```bash
npm run local -- maintenance --pause --confirm
npm run local -- collect ORIGINAL_MAINTENANCE_ID
npm run local -- web-control --confirm --storage-gib 50
npm run local -- maintenance --resume --request-id ORIGINAL_MAINTENANCE_ID --confirm
npm run local -- run
```

Используйте тот же `--state PATH` во всех командах, если он задан. Читайте тот же ID обслуживания
до известного результата: pause/resume явно прерывает физическую работу и восстанавливает намерение,
но не прерванные команды. Закрытие клиента или Ctrl+C не выполняет эту паузу.
Не используйте `disable` только
ради изменения максимума: он выключает и останавливает собственную работу. Неуказанные пределы сохраняются
из существующего одобрения. Обновите **Локальные компьютеры**, запросите хранилище 50 в редакторе
компьютера и дождитесь применённой редакции и фактической ёмкости. Одобрение само по себе не
увеличивает хранилище, не включает работу и не сбрасывает ожидающий запрос. Неудачный или
прерванный resize сохраняет прежние записи восстановления; не сбрасывайте состояние и не
создавайте кодспейсы заново. Выключенная работа не мешает управляющему соединению сообщать
одобрение, но гостевая работа требует действующего разрешения. При потере ответа одобрения
переподключитесь с тем же состоянием: сохранённое одобрение будет сообщено снова.
Прямые локальные `login`, `setup`, `recover` и одобрение веб-управления требуют физического runner gate.
При установленном владельце используйте ту же явную паузу обслуживания перед этими командами,
затем resume: приостановленный сервис сохраняет управляющий endpoint, освобождая физическое владение.
Неподдерживаемая версия
SDK, Linux runtime ownership, небезопасные mounts/settings или неизвестная identity запрещают
работу. Не сбрасывайте личный Docker-профиль, не заменяйте ограниченный том обычным каталогом
и не ослабляйте сетевую политику. Для Docker sign-in используйте `npm run local -- login`.
Нечитаемое хранилище SDK восстанавливается явно через `login --new-store` только после локального
отключения и остановки собственных процессов; существующие хранилища сохраняются.

Для обновления владельца сохраните полный пакет через `install`, проверьте `service-status`
и вызовите `maintenance --confirm`. Сохраните выведенный ID; при потере ответа читайте его через
`collect ORIGINAL_ID`. Владелец подтверждает завершение точного физического владения до выбора
подготовленного релиза. Преемник восстанавливает прежние identity VM, диски и намерение работы.
Принятые команды не повторяются; исход прерванной обслуживанием команды может остаться неизвестным.
Без подтверждённой остановки новый владелец не запускается. Сохраните результат и устраните
физический отказ; не повторяйте остановку и не меняйте ID обслуживания. После явного
`recover --confirm` выключенного устройства отправьте то же намерение обслуживания для проверки
нового подтверждения остановки. Простое чтение не выполняет восстановление.
Несовместимый клиент возвращает `LOCAL_SERVICE_MAINTENANCE_REQUIRED`, не заменяя живого владельца.

После обновления отказ строгой heartbeat schema или чтения `web-control.json` может означать разные
редакции control контракта сервера, companion и owner guard, даже при выключенном делегировании.
Пересборка CLI не заменяет живой guard или установленный исполняемый релиз.
Фиксированная подготовка гостя обновляет общий workspace service на месте.
Если подтверждение не содержит доказательства старта, этот старт остаётся неподтверждённым.
Читайте исходную
операцию; сам по себе неизвестный результат команды не требует перезапуска companion или остановки VM.
При несовместимой редакции control контракта используйте явное прерывание обслуживания и подтвердите
завершение работы. До согласованного переключения сохраните серверную базу, полное приватное
состояние companion и backing storage SDK, включая диски VM. Сохраните соответствующие бандлы,
согласуйте редакции сервера/companion и запустите выбранного владельца с прежними state и дисками.
Согласованный откат должен сохранять записи, принятые после копии; не восстанавливайте старую
базу поверх новой принятой работы.
Не удаляйте approval/журналы, не создавайте заменяющее состояние и не завершайте произвольные guard
процессы. Управление может прерваться; rolling upgrade смешанных редакций не поддерживается.
Live append внутри согласованной редакции не делает само обновление непрерывным.

Миграция 0061 архивирует старые облачные Local policy/control, relay, grants и операционные записи;
архивы не разрешают выполнение. Владелец импортирует только проверенные существующие native
bindings и сохраняет неизвестные исходы. Неподдерживаемый приватный формат владельца остаётся
отказом: сохраните холодную копию, identity, журналы и диски вместо правки облачной policy или
удаления состояния. Откат восстанавливает обе копии и согласованные бандлы. Не заменяйте
сопряжение и не сбрасывайте SDK.

Неизвестный исход команды или правки относится к принятой операции; сам по себе он не требует
остановки или восстановления всей VM. Перед повтором того же эффекта или изменением затронутых
файлов проверьте результат и эти файлы. Независимая работа не требует разрешать этот неизвестный
исход. Не повторяйте неизвестную правку автоматически и не удаляйте её журнал ради новой работы.
При отказе владельца runtime, например `LOCAL_GUEST_SETTLEMENT_UNKNOWN`, подтвердите физическую
остановку перед `npm run local -- recover SPACE_ID --confirm`. Команда проверяет точную native
identity и сетевую границу, сохраняя задачи и неизвестные исходы без повтора. При работающем владельце
сначала используйте паузу обслуживания выше, затем resume с исходным ID и при необходимости `run`.
Используйте тот же `--state PATH`. Обычные stop/start не требуют отдельного восстановления счётчиков.
Если признанный неопределённый исход возник во время первоначальной подготовки, восстановление
сохраняет исходную операцию и оставляет настройку незавершённой. Исправьте указанную предпосылку,
затем явно выполните `resume-setup WORKSPACE_REF` для той же известной VM; подтверждение не означает
завершённой настройки и не разрешает обычный start.
`npm run local -- recover --confirm` отдельно признаёт
остановку потерянного владельца выключенного устройства. Ни одна команда не удаляет данные
кодспейса и не разрешает принятие VM по имени SDK. При незавершённой остановке или неизвестной
identity сохраните записи и устраните отказ перед включением новой работы.
См. [локальную настройку](/ru/docs/getting-started/self-hosting/#подключение-локальных-кодспейсов).

## Сценарии восстановления

### Сценарий: Возобновление после прерывания

```
Пользователь: Продолжай работу над фичей авторизации

Агент:
1. session({ action: "executions", search: "auth" })
   → Найден: executionId: "abc-123", status: "waiting"

2. session({ action: "current_step", executionId: "abc-123" })
   → attemptId: "attempt-current", directive: "Реализовать endpoint логина"

3. [Выполняет работу]

4. step({ processId: "abc-123", attemptId: "attempt-current", input: { result: "done" } })
```

### Сценарий: Найти потерянный Process ID

```
Пользователь: Какие workflows я запустил?

Агент:
1. session({ action: "executions" })
   → Список всех активных executions с заметками

2. session({ action: "execution_context", executionId: "abc-123" })
   → Показывает полный контекст включая переменные
```

### Сценарий: Проверить почему Workflow застрял

```
Агент:
1. session({ action: "execution_context", executionId: "abc-123" })
   → status: "waiting", currentNodeId: "validation-step"

2. session({ action: "current_step", executionId: "abc-123" })
   → Показывает чего ожидает workflow
```
