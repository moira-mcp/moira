---
title: Self-Hosting
description: Запуск собственного экземпляра Moira через Docker Compose из готового образа
---

Запустите Moira на своей машине через Docker Compose. Основной путь скачивает готовый
образ из реестра — клонировать исходники и собирать локально не нужно.

## Требования

- Docker с плагином Compose (`docker compose`)
- Публичные `docker-compose.yml` и `.env.example`; для обычного пути не нужны сборка
  исходников, private-репозиторий, CLI SQLite на хосте или отдельный upgrade-скрипт

## Быстрый старт

Скачайте актуальные публичные self-host файлы:

```bash
MOIRA_FILES=https://raw.githubusercontent.com/moira-mcp/moira/master
curl -fLO "$MOIRA_FILES/docker-compose.yml"
curl -fLo .env.example "$MOIRA_FILES/.env.example"
```

1.  **Создайте конфиг**

    ```bash
    cp .env.example .env
    ```

    Для запуска на `localhost` значения по умолчанию работают без изменений.

2.  **Запустите контейнер**

    ```bash
    docker compose up -d
    ```

    Compose скачивает `ghcr.io/moira-mcp/moira:latest`, актуальный публичный релиз,
    и запускает контейнер.

3.  **Откройте веб-интерфейс**

    ```
    http://localhost:8080
    ```

    Ваш экземпляр также раздаёт эту документацию по адресу `http://localhost:8080/docs/`
    (и `/ru/docs/`), а MCP-эндпоинт — по `http://localhost:8080/mcp`.

При первом запуске Moira генерирует недостающие секреты и одноразовый пароль администратора.

## Конфигурация

`DEPLOYMENT_MODE=self-host` (по умолчанию) — установка для приватной команды с
открытой регистрацией и подтверждением администратором. Новый пользователь может
посмотреть статус подтверждения и выйти, но до подтверждения не получает доступ к
workflow, API-токенам, OAuth и MCP. Верификация email остаётся отдельной проверкой и
в self-host не обязательна. Недостающие секреты генерируются при первом запуске.

Администратору self-host остаётся доступна страница **Пользователи** для подтверждения,
блокировки и восстановления учётных записей. В строках также показаны записанная активность,
последний принятый шаг, если он записан, число запусков и наиболее используемые флоу. Эти сведения
управления не зависят от периодов и исключений аналитики; отсутствие записи об активности или
шаге обозначается как неизвестное. Сквозное администрирование чужих workflow,
исполнений и артефактов, облачная аналитика, операционная панель и инструменты намеренной
проверки мониторинга отключены на сервере и не показываются в навигации. Это возможности
режима установки, а не только скрытые элементы интерфейса. Политика SaaS включает их через
тот же resolver, который используют API и веб-интерфейс.
Панель self-host по-прежнему показывает состояние базы данных, определений настроек и
сверки управляемых workflow, но не запрашивает и не отображает общие показатели workflow
и исполнений всей установки.

### Подтверждение новых пользователей

В веб-интерфейсе войдите как администратор, откройте **Панель администратора → Пользователи**
и выберите учётную запись со статусом **Ожидает подтверждения**. Нажмите
**Подтвердить учётную запись** и подтвердите действие в диалоге. Во время запроса кнопка
показывает процесс, после завершения статус меняется на **Подтверждён администратором**, а
страница ожидания пользователя автоматически открывает Moira без повторного входа. На узком
экране сначала откройте навигацию Панели администратора кнопкой меню.

Эквивалентная операция API — `POST /api/admin/users/:id/approve`, а
`GET /api/admin/users` возвращает время подтверждения. Операция идемпотентна: повтор запроса
после неопределённого ответа не меняет первоначальное время и не создаёт второй переход.
Миграция помечает существующих пользователей подтверждёнными, а начальный администратор
всегда создаётся подтверждённым. Блокировка и верификация email независимы от подтверждения:
заблокированная учётная запись не получает доступ даже после подтверждения.

### Настройка почты и восстановление без неё

По умолчанию доставка писем отключена. Чтобы включить письма для сброса пароля и верификации,
настройте стандартный SMTP-сервер в `.env` и перезапустите контейнер:

```bash
EMAIL_PROVIDER=smtp
EMAIL_FROM=moira@example.com
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_REQUIRE_TLS=true
SMTP_USER=your-smtp-user
SMTP_PASSWORD=your-smtp-password
```

SMTP-аутентификация необязательна, но `SMTP_USER` и `SMTP_PASSWORD` задаются только вместе.
Для неявного TLS (обычно порт 465) используйте `SMTP_SECURE=true`; в остальных случаях
`SMTP_REQUIRE_TLS=true` требует STARTTLS. Brevo по-прежнему доступен с
`EMAIL_PROVIDER=brevo`, `BREVO_API_KEY` и `EMAIL_FROM`. При неполной или некорректной
конфигурации запуск прерывается. Режим SaaS также не запускается без реального провайдера.

С `EMAIL_PROVIDER=none` (значение по умолчанию) Moira запускается, а веб-интерфейс честно
сообщает, что восстановление пароля и почтовые действия недоступны. Администратор может
открыть карточку обычного пользователя, выбрать **Установить временный пароль** и передать
его по отдельному защищённому каналу. Действие отзывает все сессии пользователя, API-токены,
OAuth-учётные данные и согласия. Пользователь входит с временным паролем и обязан сразу его
заменить. Для учётных записей администраторов используйте описанную ниже CLI-процедуру.

`EMAIL_PROVIDER=test` предназначен только для записи писем в лог в автоматических тестах.
Он не означает настроенную доставку и не сообщает о записанном письме как об отправленном.

### Восстановление доступа администратора

В каталоге с `docker-compose.yml` задайте новый пароль так, чтобы он не попал в историю shell:

```bash
read -s ADMIN_PASSWORD
export ADMIN_PASSWORD
docker compose exec -e ADMIN_PASSWORD moira npx tsx scripts/create-admin-user.ts
unset ADMIN_PASSWORD
```

`ADMIN_PASSWORD` обязателен. Значения `ADMIN_EMAIL` и `ADMIN_ID` по умолчанию —
`admin@moira.local` и `system-admin`, а `DB_PATH` — `./data/moira.db`. Для переопределения
добавьте к `docker compose exec` аргументы `-e ADMIN_EMAIL`, `-e ADMIN_ID` или `-e DB_PATH`.
Команда создаёт или восстанавливает администратора, помечает email и учётную запись
подтверждёнными, снимает блокировку и заменяет credential. Пароль в вывод не попадает.

### Откат на версию без подтверждения учётных записей

Старый образ не учитывает `approvedAt`. Перед закреплением такого образа остановите внешний
трафик, создайте резервную копию базы и выполните преобразование на текущем образе:

```bash
docker compose exec moira npm run prepare:account-approval-downgrade -- \
  --confirm-block-pending-users
```

Без аргумента подтверждения команда отказывается работать. В одной транзакции она блокирует
каждого ожидающего пользователя через старое поле `blocked` и отзывает его сессии, API-токены,
OAuth-токены и OAuth-согласия. Проверьте выведенные счётчики до остановки текущего контейнера.
Не выполняйте откат раньше преобразования: старый образ не умеет его делать. При возврате на
версию с подтверждением сначала проверьте каждую преобразованную учётную запись, а затем
подтвердите и явно разблокируйте её.

### Переменные, зависящие от хоста

Эти три должны указывать на ваш хост и иметь согласованные порты. Значения по умолчанию
нацелены на `localhost:8080`, поэтому для запуска на localhost правки не нужны.

| Переменная                | По умолчанию            | Назначение                                           |
| ------------------------- | ----------------------- | ---------------------------------------------------- |
| `MOIRA_HOST`              | `localhost:8080`        | Публичный хост (протокол определяется автоматически) |
| `MOIRA_PORT`              | `8080`                  | Порт хоста, проброшенный в контейнер                 |
| `STATIC_ARTIFACTS_DOMAIN` | `static.localhost:8080` | Домен для размещаемых HTML-артефактов                |

Для реального хоста или другого порта меняйте все три вместе:

```bash
MOIRA_HOST=moira.example.com
MOIRA_PORT=8080
STATIC_ARTIFACTS_DOMAIN=static.example.com
```

:::caution
`STATIC_ARTIFACTS_DOMAIN` обязателен — при пустом значении запуск прерывается.
:::

### За обратным прокси

Лимиты запросов, исключение `RATE_LIMIT_WHITELIST`, записи аудита и адреса сессий Moira привязывает к
адресу клиента. Этот адрес она берёт из `X-Forwarded-For` только через прокси, перечисленные в
`TRUST_PROXY`; записи, которые клиент дописал сам, не используются никогда.

- Без значения (по умолчанию) доверяется только nginx внутри контейнера. Так нужно, когда клиенты
  подключаются к опубликованному порту контейнера напрямую.
- За ещё одним обратным прокси — Traefik, Caddy, балансировщиком — укажите число прокси-хопов или
  адрес либо подсеть этого прокси:

```bash
TRUST_PROXY=2                            # ваш прокси, затем nginx внутри контейнера
TRUST_PROXY=loopback,172.18.0.0/16       # или: loopback плюс Docker-сеть прокси
```

Без этой настройки все клиенты за вашим прокси получают его адрес и один общий лимит запросов.
`TRUST_PROXY=true` не принимается, а при неверном значении запуск прерывается с ошибкой, в которой
перечислены допустимые формы.

### Автогенерируемые секреты

В режиме self-host они генерируются при первом запуске и сохраняются в
`<data-dir>/.secrets.env`. Оставьте их пустыми в `.env`:

| Переменная                | Сгенерированное значение                         |
| ------------------------- | ------------------------------------------------ |
| `BETTER_AUTH_SECRET`      | Ключ шифрования сессий                           |
| `TELEGRAM_ENCRYPTION_KEY` | Ключ шифрования учётных данных Telegram          |
| `ADMIN_PASSWORD`          | Пароль администратора, выводится в логи один раз |

Данные для входа администратора выводятся в логи контейнера один раз при первом запуске:

```bash
docker compose logs | grep -A3 "ADMIN LOGIN"
```

Войдите с `ADMIN_EMAIL` (по умолчанию `admin@moira.local`) и выведенным паролем.

### Подключение локальных кодспейсов

**Настройки → Разработка → Локальные компьютеры** связывают компьютер с Moira Local и этим
аккаунтом. Локальные окружения и GitHub используют общий инструмент `codespace`. Сопряжение,
чтение публичных репозиториев и базовая локальная работа не требуют GitHub App и серверного
хранилища credentials. Доступ сопряжённого устройства к приватным репозиториям, push и операции
PR требуют серверного OAuth-подключения GitHub App и настроенного хранилища. Локальной работе
не нужен описанный ниже профиль коннектора Compose. Companion инициирует исходящие
HTTPS-запросы и не открывает публичный порт.
Серверная работа по-прежнему требует `CODESPACE_CODESPACES_ENABLED=true` и включённых instance controls.

Нужны Node.js 24, macOS на Apple silicon и подписанный Docker Sandboxes `sbx` 0.46.0 из
[официальных release artifacts](https://github.com/docker/sandboxes/releases/tag/v0.46.0).
См. [требования установки Docker](https://docs.docker.com/ai/sandboxes/install/).
Исполнение на Linux отклоняется. Соберите приватный пакет companion из checkout Moira
при доступном command-line C compiler macOS;
опубликованного глобального npm installer нет:

```bash
npm ci
npm run local:build
npm run local -- init --sbx /absolute/path/to/Sbx.app/Contents/MacOS/sbx --label My-computer
npm run local -- login
npm run local -- setup
npm run local -- approve OWNER/REPO
npm run local -- enable --hours 8
npm run local -- doctor
```

`init` создаёт приватное состояние и дисковый образ с ограниченной ёмкостью; работа выключена.
Образ монтируется по короткому пути собственного устройства, чтобы сокеты SDK помещались в
системный предел. `--state PATH` выбирает другой каталог состояния; повторяйте его в каждой
команде. `--storage-gib`, `--cpus` и `--memory-gib` задают выделенные ресурсы
при инициализации. `setup` требует пустой выделенный профиль SDK. `doctor` проверяет предпосылки
при включённом неистёкшем разрешении на работу; `liveVmIsolationVerified: false` не является
результатом проверки изоляции настоящей microVM.

Companion хранит Docker sign-in в отдельном зашифрованном хранилище SDK и не изменяет выбор
личного Docker-профиля или Keychain. Для восстановления хранилища сначала отключите локальную
работу и остановите companion, затем выполните `npm run local -- login --new-store`.
Это явное действие проверяет остановку собственных процессов, создаёт отдельное хранилище
и сохраняет существующие credentials. Ошибка не вызывает автоматическую ротацию или импорт
личных credentials.
Это машинное хранилище доверяет аккаунту хоста: сгенерированный пароль хранится в локальном файле,
доступном только владельцу; блокировка при sleep/по интервалу выключена только для хранилища SDK,
а не личной Keychain.

Права на репозиторий выдаются на компьютере. `approve OWNER/REPO` разрешает чтение.
Добавляйте `--private`, `--push` и `--delete` только для соответствующих прав.
Для самостоятельной работы без сопряжения приватный репозиторий может использовать GitHub-токен,
переданный через stdin в `npm run local -- git-token OWNER/REPO`; не помещайте его в аргументы
или историю shell. Этот токен остаётся локальным и отделён от credential устройства. Сопряжённый
companion, обслуживающий Moira, использует серверную OAuth-авторизацию для приватного доступа и
push и не переключается на этот локальный токен.
Конечный срок работы по умолчанию составляет 8 часов и не может превышать семь дней.
Продлевайте его локально через `enable --hours N`. Браузер может менять эти настройки только
после явного разрешения веб-управления на компьютере, описанного ниже.

В **Локальных компьютерах** выберите **Подключить устройство**. Скопируйте показанную команду
и токен сопряжения отдельно. В checkout выполните её через
`npm run local -- enroll --server <показанный HTTPS URL приложения> --pairing-id <показанный ID>`.
Введите токен в stdin и завершите ввод; не дописывайте его в команду. URL сервера включает
настроенный префикс приложения и не содержит credentials, query или fragment.
Обновите браузер, проверьте репозитории ожидающего компьютера, права push/delete,
выделенные ресурсы и срок разрешения, затем подтвердите подключение.

Сервер, companion и работающие owner guards должны использовать согласованную редакцию control
контракта. Строгие heartbeat/approval schemas не принимают смешанные редакции даже при выключенном
делегировании; пересборка CLI не обновляет живой guard. Перед обновлением штатно остановите
companion владельческим путём и подтвердите завершение его работы и guards. Согласованно обновите
сервер и локальный checkout только после резервного копирования при остановленных обеих сторонах:
сохраните серверную базу, полный приватный каталог companion и backing storage SDK, включая диски
VM. Вместе с копией сохраните согласованные серверный и локальный бандлы. Выполните `npm ci` и
`npm run local:build`, затем штатно перезапустите.
Сохраните прежние state, диски, SDK profile, credentials и соединение. Управление и работающие
задачи могут прерваться; непрерывного rolling upgrade смешанных редакций нет. Live append
репозитория внутри согласованной редакции отдельно сохраняет существующие VM.

Если сохранённый формат управления содержит неподдерживаемые поля, создайте резервную копию
серверной базы и приватного состояния и дисков компьютера, затем преобразуйте только эти поля
при остановленных обеих сторонах. Удалите списки доменов репозитория, поля количества репозиториев
и сетевого профиля в делегировании и технические квоты из всех сохранённых policy, control и
ожидающих intent, включая делегирование сохранённых запросов создания репозитория. Сохраните
grants, подтверждения и маркеры запросов, ID, поколения, задачи, credentials и диски. Проверьте
строгий формат перед запуском согласованных серверного и локального бандлов. Digest публичной
policy на сервере должен соответствовать преобразованному каноническому JSON. Автоматического
чтения неподдерживаемого формата нет. Откат восстанавливает обе копии и соответствующие бандлы;
сброс SDK или новое сопряжение не требуются.

После подтверждённого сопряжения разрешите локальное веб-управление:

```bash
npm run local -- web-control --confirm --max-lease-hours 168
```

Используйте тот же `--state PATH`, что при настройке. Неуказанные числовые пределы сохраняют
текущие локальные значения; предел срока этой команды по умолчанию — семь дней. Чтобы разрешить
большие ресурсы, задайте нужные пределы через `--cpus`, `--memory-gib`, `--storage-gib`
и `--docker-gib`. Само одобрение не продлевает срок работы.
Повтор этой команды не заменяет существующее одобрение веб-управления; запросы браузера должны
укладываться в сохранённые пределы.
Запустите companion на переднем плане после подтверждения и локального одобрения:

```bash
npm run local -- run
```

В **Локальных компьютерах** редактируются имя, включение работы, срок, CPU/RAM, ограниченный
диск и ёмкость гостевого Docker, права репозиториев, автор коммитов. **Разрешить семь дней**
задаёт конечный срок в пределах локального одобрения; автоматического продления нет.
Команда передаёт ограниченные таймаут и размер вывода без отдельных владельческих квот операций.
**Запросить изменение настроек** сохраняет запрос, а не действующие права. Ожидающий запрос
ждёт компьютера; применённая и отклонённая редакции показывают результат companion. Перед работой
проверьте действующие разрешения над редактором. Ошибки сохраняют черновик; обновления меняют
нетронутые поля, сохраняя независимые правки. Управляющее соединение может получить продление,
когда работа выключена или срок истёк, но гостевая работа остаётся выключенной до применения.
CPU/RAM и гостевой Docker задают профиль новых сред; существующие VM сохраняют принятый профиль.
Ёмкость хранилища задаёт общий дисковый образ SDK на компьютере, а не отдельный диск такого
размера для каждого кодспейса.
Изменение ограниченного диска требует остановки собственных процессов и проверенного resize;
отказ не разрешает дальнейшую работу и не удаляет данные.
Для приватных репозиториев, push и создания PR через Moira подключите GitHub и предоставьте App
доступ к репозиторию. Эти операции также требуют соответствующих прав репозитория устройства;
чтение метаданных PR использует право чтения репозитория. GitHub authorization остаётся на сервере,
а не в госте. Укажите автора коммитов или оставьте оба поля пустыми для проверенной GitHub identity,
когда она доступна; Git-конфигурация компьютера не копируется.

После локального одобрения web control владелец может здесь включить управление
репозиториями для агента. По умолчанию оно выключено; разрешение привязано к проверенному личному
GitHub-аккаунту, отдельным правам на существующие/новые приватные репозитории и push.
Квоты количества репозиториев или фиксированного профиля технологий нет.
Разрешение действует только после подтверждения companion.
`codespace({ action: "local_devices" })` показывает применённое разрешение и подходящие личные
installation App; `github_setup_required` указывает на настройку GitHub, сохраняя список устройств. `repository_add`
принимает `device_id`, числовой GitHub `repository_id` и постоянный UUID `request_id`.
Повторяйте тот же запрос до `applied` с `local_repository_id`; pending/rejected не дают доступ.
Репозиторий уже должен быть доступен App. Добавление сохраняет прежние права, VM и срок;
агент не меняет consent и не задаёт права.
Для нового пустого приватного репозитория включите и примените new-private consent, затем вызовите
`repository_create` с `device_id`, постоянным UUID `request_id`, `repository_name` и найденным
`installation_id`. Поддерживается только подключённый личный аккаунт. Продолжайте тот же полный
запрос: `unknown` не повторяет создание вслепую; `setup_required` может сохранить подтверждённые
GitHub ID/имя до исправления permissions или installation access. Пригодный `local_repository_id`
возвращается только с `applied`. Selected installation получает лишь подтверждённый новый репозиторий,
после чего доступ проверяется. Unknown сохраняет точную identity восстановления и не блокирует
добавление других репозиториев.
Если ошибка содержит `error.stage`, это этап отказа настройки; `error.provider_status` — HTTP-статус
GitHub. Выполните возвращённую `instruction`. Отклонённый локальный допуск может сохранить уже
созданный репозиторий: восстановите исходный grant в Настройках либо вызовите `repository_add`
с сохранённым GitHub ID и новым `request_id`, если разрешён допуск существующих приватных
репозиториев. Один повтор отклонённого допуска не восстанавливает доступ; не создавайте другой репозиторий.
Description приватного репозитория содержит recovery marker, а не credential. Сохраняйте его,
пока неизвестный исход не разрешён; Moira не присваивает посторонний same-name репозиторий.

Владелец должен одобрить **Repository creation: write** либо **Administration: write** для
[create API](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user)
и **GitHub App installation repository access: write** для
[selected installation](https://docs.github.com/en/rest/apps/installations#add-a-repository-to-an-app-installation).
Одобренный push требует Contents write. После одобрения используйте **Обновить права GitHub**;
OAuth остаётся на сервере. Настоящие permissions App и совместимость provider требуют отдельной проверки.

У каждого кодспейса своя VM; один репозиторий может иметь несколько кодспейсов.
Локальные VM и операции не занимают облачные слоты Codespaces и не ограничиваются облачным
машинным профилем. Фоновый `exec` запускает процессы разработки внутри VM. Публичные реестры пакетов
и другие публичные DNS-адреса доступны независимо от языка или фреймворка; каждое соединение
проверяет публичность адреса и исключает сети компьютера. У сетевых загрузок нет накопительной квоты
трафика или квоты размера файла; ограниченная ёмкость сокетов создаёт очередь ожидания.
Адреса компьютера, локальной сети и служебных сетей остаются запрещены. Браузер и системные
библиотеки устанавливаются гостевыми командами с подходящими правами; доступ к сети не подтверждает
совместимость браузера.
`preview_image` возвращает PNG/JPEG из репозитория как нативное MCP-изображение: передайте
`codespace_id`, `path` и при необходимости `max_bytes` до 4 MiB либо продолжите только с
`codespace_id` и `operation_id`. Проверки заголовка/контейнера ограничивают изображение 8192
по стороне и 16 миллионами пикселей, но не декодируют все пиксели. Осмотрите изображение,
прежде чем считать скриншот визуальным свидетельством.

В **Настройки → Разработка → Локальные компьютеры** откройте кодспейсы подключённого компьютера
и выберите одобренный репозиторий для создания VM либо получите
его qualified `repository_id` через `codespace({ action: "list" })`. Один репозиторий на разных
компьютерах — разные варианты выбора. Дальнейшая работа использует существующие
`codespace_id`, контракты исполнения, сессий, файлов и native transfer. Провайдер GitHub
остаётся независимым. Настройки позволяют отозвать отдельное устройство; **Обновить** перечитывает
текущее состояние. Отзыв в браузере запрещает новую серверную работу, но не подтверждает
физическую остановку недоступного компьютера; локальное отключение и истечение разрешения
обеспечивают независимую остановку.

В карточке каждого компьютера находятся его форма создания, кодспейсы и свёрнутые настройки.
Компьютеры с одинаковым названием не смешиваются; у одного репозитория может быть несколько
отдельных VM. Общая ёмкость хранилища показана у компьютера, CPU и RAM — у каждой VM. GitHub
Codespaces находится в отдельном подразделе. Обновление и ошибки действий принадлежат
соответствующей секции или кодспейсу. Локальные карточки показывают время последнего проверенного
наблюдения либо его отсутствие и локализованную причину отказа. **Проверить состояние снова**
повторяет существующее намерение запуска, остановки или удаления точного кодспейса; ожидающее
создание только перечитывается. `created` не подтверждает остановку: независимый native owner
должен проверить точный runtime и завершение его worker. Недоступное наблюдение сохраняет
последнее проверенное состояние и не превращается в успешную остановку.

**Удалить** доступно при ожидающем создании, очистке и неопределённом локальном состоянии, с явным
подтверждением и текущим поколением. Действие адресует ту же собственную VM и ждёт подтверждённого
удаления; отказ наблюдения не позволяет убрать карточку как отсутствующую VM. Ошибка одной
карточки не мешает обновлению и работе исправных соседних кодспейсов.
Физический запуск VM отличается от готовности гостя: команды доступны только после завершения
его подготовки. `CODESPACE_LOCAL_SETUP_INCOMPLETE` означает незавершённую подготовку, даже если
VM подтверждённо остановлена. Удалите её и дождитесь подтверждения перед созданием замены;
перезапуск и `recover` не завершают первоначальную настройку.

Устанавливайте согласованные сборки сервера и companion. Их строгий контракт snapshot и
результатов управления включает точную identity создания, готовность гостя и подтверждение
native-остановки. Запись не считается наблюдённой до проверенного чтения. Используйте описанные
выше остановку и резервное копирование; откат восстанавливает согласованные серверную базу,
полное локальное состояние, хранилище SDK и бандлы вместе. Неподдерживаемый сохранённый формат
policy/control преобразуется только при остановленных обеих сторонах.

CLI-команды create/start/exec с manager одноразовые: при выходе останавливают собственные VM-процессы.
Постоянная серверная работа использует `run`; остановите его перед другой командой с тем же runner lock.
Локальный daemon отделяет связь с сервером от времени жизни VM. При сетевой ошибке/5xx он
переподключается; некорректный ответ управляющего соединения приостанавливает новые запросы
до успешного подтверждения, сохраняя принятую работу. Адресный отказ ресурса или доставки остаётся
в пределах этого запроса: фоновая доставка подтверждает прежние действующие права устройства
и продолжает независимые запросы без общего сбоя daemon и задержки повтора.
Подтверждённый отзыв/смена identity устройства,
локальное отключение и истечение срока останавливают работу. Права и сроки не продлеваются;
возврат сохранённого результата не повторяет эффект.
Ctrl+C закрывает companion; `npm run local -- disable` независимо останавливает собственную
работу и сохраняет данные VM. Stop сохраняет файлы, а `remove SPACE_ID --confirm` удаляет
точную собственную VM. Неопределённый исход гостевой операции блокирует дальнейшую работу,
а не вызывает автоматический повтор. После подтверждённой остановки VM
`recover SPACE_ID --confirm` признаёт этот исход без повтора задач. Команда также подтверждает
поколение инициализированной остановленной VM без ошибки при конфликте с серверной привязкой,
проверив точную identity и сетевую политику. Используйте тот же каталог состояния и перезапустите
`run`; прежние задачи и неизвестные исходы сохраняются. Обычная подтверждённая остановка без
ошибки сохраняет подтверждение поколения автоматически. Для потерянного владельца
процессов команда `recover --confirm` требует выключенной работы, подтверждает физическую
остановку и сохраняет задачи и данные.
См. [Решение проблем](/ru/docs/integration/troubleshooting/#локальные-кодспейсы).

У локальных VM нет host mounts, общих skills, host MCP gateway или перенаправленных credentials,
environment и agent sockets хоста. Внешняя политика SDK запрещает host/LAN/VPN/metadata/other-VM
доступ и прямой egress; допускается только локально одобренный публичный egress через broker.
Публичные SDK placeholders для API/GitHub в гостевых переменных не являются токенами пользователя.
Проверки от root гостя наблюдают host canaries и доставку challenge на доступные loopback/LAN/VPN
интерфейсы; соединение с proxy само по себе не означает доставку. Эти наблюдения не доказывают
физическую изоляцию удалённого VPN-маршрута, metadata-сервиса или другой VM без доступных
контролируемых целей. Такие внешние проверки на стенде не исполнены. Содержимое кодспейса
намеренно видно Moira; проверяйте возвращённый код перед запуском на компьютере.

### Включение подключения GitHub для кодспейсов

Подключение GitHub для кодспейсов не связано с социальным входом через GitHub. Оно
остаётся отключённым, пока не заданы все корректные значения GitHub App и хранилища учётных
данных. Создайте GitHub App, включите истекающие user authorization tokens и «Request user
authorization (OAuth) during installation», выдайте ему права на репозитории Codespaces (write),
Codespaces lifecycle admin (write), Codespaces metadata (read), Contents (write), Pull requests (write) и Metadata (read),
укажите точный API-путь Moira для callback и URL установки с GitHub slug приложения. Setup URL не
нужен: после установки GitHub возвращает браузер на callback URL:

```bash
CODESPACE_GITHUB_APP_CLIENT_ID=<github-app-client-id>
CODESPACE_GITHUB_APP_CLIENT_SECRET=<github-app-client-secret>
CODESPACE_GITHUB_APP_CALLBACK_URL=https://moira.example.com/api/integrations/github/callback
CODESPACE_GITHUB_APP_INSTALL_URL=https://github.com/apps/<github-app-slug>/installations/new
CODESPACE_CREDENTIAL_VAULT_KEY=<случайный-64-значный-hex-ключ>
CODESPACE_CREDENTIAL_VAULT_KEY_VERSION=v1
```

Создайте отдельный ключ хранилища вне репозитория и поместите результат в незатреканное окружение
деплоя:

```bash
openssl rand -hex 32
docker compose up -d
```

Origin callback должен совпадать с публичным origin Moira. Публичный callback использует HTTPS и
не содержит query или fragment. Используйте client secret, созданный GitHub: placeholder,
повторяющиеся символы и другие значения с низким разнообразием отклоняются. Ключ хранилища не
генерируется автоматически и должен оставаться неизменным между перезапусками контейнера; после
его замены существующие credentials подключения нельзя прочитать.

Если ключ или ciphertext потерян, обычные переподключение и отключение не могут подтвердить
удалённый отзыв. Сначала удалите grant приложения Moira GitHub App в настройках GitHub. Затем
вернитесь в **Настройки → Разработка → Подключение GitHub** и выберите **Удалить после внешнего отзыва** в карточке GitHub.
Подтверждение удаляет нечитаемый локальный ciphertext; не подтверждайте, пока grant виден в GitHub.
Если исходные ключ и версия восстановлены, Moira больше не предлагает восстановление для
нечитаемого credential. Обычные **Переподключить GitHub** и **Отключить** снова доступны; оба
действия точно отзывают читаемый предыдущий credential.

Такое же подтверждение внешнего отзыва появляется, если обновление могло вернуть новый credential,
который Moira не смогла сохранить или отозвать. Перед подтверждением отзовите весь grant GitHub App;
в этом состоянии переподключение и обычное отключение намеренно недоступны.

После выхода контейнера в healthy каждый пользователь открывает **Настройки → Разработка → Подключение GitHub**,
нажимает **Подключить GitHub** и один раз авторизуется в GitHub. Если приложение ещё не
установлено в аккаунте, браузер сразу переходит на страницу установки GitHub; после установки для
нужных личных репозиториев настройки показывают подключение без повторной авторизации. Если
возврат не пришёл, **Проверить установку** заново читает установку. Чтобы сменить аккаунт GitHub,
отключитесь и подключитесь снова. Авторизация никогда не выполняется через MCP-инструмент или
агента.
Если настройка отсутствует или credential нужно обновить, пользователь возвращается на этот сайт.

Для создания кодспейсов GitHub и операций агента дополнительно требуются
`CODESPACE_CODESPACES_ENABLED=true` и пара коннектора из отключённого по умолчанию профиля Compose:

```bash
docker compose --profile codespaces up -d
```

После настройки подключения и коннектора аутентифицированный MCP-клиент использует один инструмент
`codespace`, выбирая операцию полем `action`: `list` показывает одобренные репозитории и существующие
кодспейсы и обновляет устаревшие разрешения, `setup_help` возвращает текущий шаг пользователя и точные
ссылки провайдера, `create` создаёт постоянный Codespace с личным биллингом для одобренного репозитория, а
`exec`, `stat`, `search`, `read`, `write`, `apply_patch`, `upload` и `download` работают внутри него по
`codespace_id`. `stop` сохраняет данные репозитория; `delete` удаляет Codespace
и требует явного подтверждения. Разные чаты и клиенты могут использовать один кодспейс; ничего
не удаляется при завершении команды или отключении клиента.

Агент в кодспейсе действует как обычный пользователь Codespace: он может читать
репозиторий, использовать сеть и читать секреты, настроенные для этого Codespace. Изоляция Moira
защищает сервер Moira и других пользователей, а не кодспейс от агента, которого авторизовал его
владелец. Если настройка не завершена, отказ содержит те же применимые ссылки на Настройки,
создание репозитория и консоль провайдера, что и `setup_help`, а при настроенном URL — также ссылку
на установку приложения; авторизация при этом не запускается.
Кодспейс остаётся личным, а совместная работа идёт через ветки системы контроля версий.

Теми же кодспейсами пользователи управляют в карточке **Среды разработки** раздела **Настройки →
Разработка → GitHub Codespaces**: создают кодспейс для одобренного репозитория, запускают или останавливают его
(остановка сохраняет данные репозитория) и удаляют после явного подтверждения. Простаивающие
кодспейсы каждого пользователя приостанавливаются сами: карточка **Автоматическая приостановка** в
том же разделе задаёт `codespaces.auto_stop_enabled` (по умолчанию включена) и
`codespaces.idle_timeout_minutes` (по умолчанию 30, от 5 до 240), которые определяют, когда Moira
останавливает кодспейс, которым ни один агент не пользовался через Moira, а следующая операция
агента снова его запускает. Карточка **Ваши лимиты** рядом показывает лимиты пользователя на
кодспейсы, команды и передачи относительно текущего использования. Прямая работа в браузере,
редакторе или по SSH не видна, поэтому тем, кто работает в кодспейсах напрямую, стоит выключить
приостановку.
Администраторы открывают **Админ → Настройки → Кодспейсы**, чтобы увидеть готовность инстанса
(конфигурация, коннектор, очередь согласования, активные кодспейсы и операции относительно
лимитов) и приостановить работу глобальным или провайдерским аварийным контролем; приостановка
отклоняет новые кодспейсы, запуски и операции агентов и останавливает работающие кодспейсы,
ничего не удаляя.

Для мониторинга `GET /api/health` и эндпоинт MCP `/health` сообщают состояние готовности
(`disabled`, `misconfigured`, `control_disabled`, `connector_unavailable` или `ready`); отключённая
функция считается здоровой, а неверная конфигурация или недоступный коннектор помечают инстанс как
degraded. Health отвечает из кэшированного решения, обновляемого с интервалом согласования, а
проверка коннектора ограничена двумя секундами, поэтому зависший коннектор не подвешивает health. Внутренний порт метрик отдаёт gauge и счётчики `moira_codespace_*`. Оповещайте, когда
`moira_codespace_ready` остаётся 0 при `CODESPACE_CODESPACES_ENABLED=true`, когда
`moira_codespace_connector_available` равен 0, когда
`moira_codespace_reconciliation_oldest_due_age_seconds` превышает несколько интервалов согласования
или когда `moira_codespace_rejections_total` растёт по кодам квот или занятости.

Отключение запрещает локальное использование до отзыва доступа в GitHub. Если GitHub временно
недоступен, страница показывает незавершённый отзыв, а кнопка **Отключить** повторяет операцию по
точной зашифрованной capability; credential не возвращается в браузер или модели.


## Обновление и восстановление

Для обычного обновления не требуется искать версию или запускать скрипт из репозитория:

```bash
docker compose pull
docker compose up -d
docker compose ps
```

Если существующий `.env` создан из старого сломанного шаблона и всё ещё содержит удалённый тег
`0.3.5`, один раз замените строку перед обновлением:

```bash
MOIRA_IMAGE=ghcr.io/moira-mcp/moira:latest
```

До запуска миграций нового self-host образа startup guard создаёт online backup существующей SQLite
БД и проверяет `PRAGMA integrity_check`. База вместе с соответствующим `prompt-manifest.json`
сохраняется в `data/.moira-startup-backups/current/`, а предыдущие состояния ротируются в
`previous-1/` и `previous-2/`. При настоящем первом запуске БД ещё нет, поэтому backup не создаётся.

В current-слоте хранится persistent-маркер незавершённой инициализации. Если контейнер или хост
прерывается до фиксации результата, следующий запуск сначала восстанавливает проверенный slot и
только затем создаёт новый backup, поэтому частично мигрированная БД не становится новым baseline.
На первом запуске отдельный marker без фиктивной backup-БД фиксирует, что базы раньше не было. После
прерывания повторный запуск удаляет только незавершённые новую БД, WAL/SHM и prompt manifest и
начинает с чистого состояния; успешная инициализация удаляет marker.

Если инициализация схемы, промптов или workflow завершается ошибкой после записи данных, guard
удаляет WAL/SHM, восстанавливает проверенные БД и manifest, пишет `/tmp/init-failed` и не запускает
MCP, API и nginx. Recovery-копия сохраняется. После исправления конфигурации или каталога проверьте
состояние и повторите запуск:

```bash
docker compose logs moira
docker compose exec -T moira sqlite3 /app/data/moira.db 'PRAGMA integrity_check;'
docker compose exec -T moira sqlite3 /app/data/.moira-startup-backups/current/moira.db 'PRAGMA integrity_check;'
docker compose restart moira
docker compose ps
```

`latest` намеренно следует за текущим публичным релизом. Автоматическое восстановление защищает
постоянные данные, но не может заменить сам Docker-образ. Если образ не доходит до startup guard,
БД не мигрировалась. Временно укажите в `MOIRA_IMAGE` предыдущую версию из
[GitHub Releases](https://github.com/moira-mcp/moira/releases), выполните `docker compose up -d`,
а после исправленного релиза вернитесь на `latest`.

Обновление, изменяющее встроенный workflow, может оставить приостановленное внутри него выполнение
без возможности продолжиться. Старт называет такие выполнения до применения обновления — workflow,
выполнение и ноду, на которой каждое стоит, — поэтому они видны в `docker compose logs moira`, пока
прежние определения ещё на месте. Предупреждение никогда не останавливает обновление. Выполнение,
ставшее непригодным из-за изменения workflow, можно затем восстановить через
`session({ action: 'diagnose', ... })` и `session({ action: 'recover', ... })`; выполнение, чей
workflow обновление удаляет, восстановить нельзя — возобновляться не на чем, — и строка сообщает,
какой это случай. Отсутствие предупреждения означает, что ни одно приостановленное выполнение не
пострадает.

Когда обнаружение конфликта создало локальный bundle в `data/.moira-reconciliation/pending`,
выполните его `AGENT INSTRUCTIONS` через одноразовые Compose CLI-контейнеры. Сам CLI не останавливает
и не перезапускает сервисы и не подменяет snapshot базы. Он использует только локальные файлы — без
`--force`, MCP, HTTP API и UI-транспорта. Инициализация завершается fail-closed: после восстановления
БД контейнер останавливается, а MCP, API и nginx остаются недоступны. После применения bundle
финальная команда `docker compose up -d` запускает остановленный контейнер обычным способом.

```bash
docker compose run --rm moira npm run reconcile -- status
docker compose run --rm moira npm run reconcile -- diff --reference owner/slug
# Прочитайте previous.json, current.json и incoming.json по выведенным путям.
# Запишите revision-bound решение current, incoming или merged для каждого конфликта:
docker compose run --rm moira npm run reconcile -- choose \
  --reference owner/slug --selection incoming --revision REVISION \
  --rationale "Incoming заменяет локальный эксперимент"
docker compose run --rm moira npm run reconcile -- apply
docker compose up -d
```

Для слияния возьмите `incoming.json` за основу, перенесите только всё ещё нужное локальное намерение
из `previous.json → current.json`, проверьте полный merged state через `reconcile validate` и передайте
его в `choose --selection merged --file ...`. `choose` меняет только локальный decisions manifest.
Только `apply` изменяет базу и отказывается работать с неполным или устаревшим manifest.

### Необязательный preflight до остановки

Оператор может заранее проверить точный образ на изолированной копии БД, скачав advanced helper из
этого релиза. Это необязательный путь; обычное обновление использует две Compose-команды выше. CLI
`sqlite3` на хосте нужен только для advanced-варианта.

```bash
RELEASE_VERSION=x.y.z
TARGET_IMAGE=ghcr.io/moira-mcp/moira:${RELEASE_VERSION}
curl -fLo self-host-upgrade.sh "https://raw.githubusercontent.com/moira-mcp/moira/v${RELEASE_VERSION}/scripts/self-host-upgrade.sh"
chmod +x self-host-upgrade.sh
./self-host-upgrade.sh preflight "$TARGET_IMAGE"
./self-host-upgrade.sh upgrade "$TARGET_IMAGE"
```

Helper сохраняет проверенный snapshot и диагностическую копию в `.moira-upgrade/`; если замена или
health check завершились ошибкой, используйте `./self-host-upgrade.sh rollback`. Advanced-путь
записывает точный образ в `.env`; чтобы вернуться в обычный release channel, после проверки задайте
`MOIRA_IMAGE=ghcr.io/moira-mcp/moira:latest`.

## Включение расширений

Для расширений нужен checkout исходников: образ сопутствующего runner собирается локально, а
опубликованный образ приложения Moira остаётся без изменений. Из корня репозитория выполните:

```bash
cp .env.example .env
mkdir -p extensions
cp -R examples/extensions/webhook-notify extensions/
```

В скопированном манифесте замените зарезервированный `example.com` и в верхнеуровневом
`permissions.network`, и в `permissions.network` канала коммуникации на точный хост своего
эндпоинта. Разрешения ноды и канала независимы. Адрес, получателя уведомлений по умолчанию и
остальные значения каждый пользователь заполняет на странице настроек Moira. Затем добавьте адрес
runner в `.env` и включите профиль:

```bash
printf '\nMOIRA_EXTENSION_RUNNER_URL=http://moira-extension-runner:9110\n' >> .env
docker compose --profile extensions up -d --build
```

Профиль собирает runner, монтирует `./extensions` в его контейнер только для чтения, ждёт готовности
runner и затем запускает Moira. Обычный `docker compose up -d` runner не запускает.

Runner и Moira загружают каталог расширений при старте. После изменения установленных бандлов:

```bash
docker compose --profile extensions up -d --force-recreate --wait moira-extension-runner
docker compose --profile extensions restart moira
```

Причины отказа и живой каталог можно проверить, не публикуя порт runner:

```bash
docker compose --profile extensions logs moira-extension-runner
docker compose --profile extensions exec moira-extension-runner curl -fsS http://127.0.0.1:9110/health
```

Пустой каталог допустим. Health-ответ перечисляет загруженные типы нод и ID каналов коммуникации.
Если Moira сообщает о недоступном реестре, проверьте URL, health и логи, затем перезапустите обе
службы в показанном порядке. Если отсутствует отдельный вклад расширения, найдите причину отказа его
манифеста. Полный контракт манифеста, SDK, разрешений, настроек, редактора, доставки, результатов,
ошибок и безопасности описан в [Написании
расширения](/ru/docs/guides/writing-extensions/).

## Добавление собственных workflow-флоу

В образе есть встроенный каталог workflow в `./workflows/production`. Чтобы дополнительно
загрузить свои флоу, задайте `WORKFLOWS_DIRS` — список базовых каталогов каталога через
двоеточие (каждый со структурой `flows/<uuid>.json`):

```bash
WORKFLOWS_DIRS=./workflows/production:./my-private-workflows/production
```

Каталоги объединяются и дедуплицируются по `(owner, slug)`. **Поздний** каталог
переопределяет ранний при коллизии, поэтому каталог, указанный последним, может
расширять или перекрывать встроенный. Не задан → только встроенный
`./workflows/production`. Смонтируйте дополнительный каталог в контейнер (например, через
volume в compose), чтобы путь существовал во время выполнения.

## Сборка из исходников

Локальная сборка — альтернатива для контрибьюторов, которым нужно изменить образ.
В `docker-compose.yml` закомментируйте строку `image:` и раскомментируйте блок `build:`,
затем:

```bash
docker compose up -d --build
```
